Progressive Shells

Instant shells & MPA navigation upgrades without a JS router

Explainer: https://github.com/WICG/declarative-partial-updates/blob/main/progressive-shell-explainer.md. Extra focus on the MPA/SPA problem space and the alternatives considered.

The Architectural Dilemma

MPAs

  • Simple mental model
  • Zero client router JS
  • Frozen screen on click
  • Full state loss on swap

SPAs

  • Immediate UI feedback
  • Preserves shell state
  • Heavy JS bundle tax
  • Slow cold starts

Authors are forced to choose between simple server-rendered MPAs (which suffer from frozen navigations and lost DOM state) and complex JS SPAs (which pay a heavy hydration and bundle cost just to keep a header and sidebar alive).

Problem 1: The MPA "Frozen Frame"

  • Paint holding freezes the old page while waiting for the new response
  • The page looks interactive, but clicks, typing, and scrolling are dead
  • If the network takes >100ms, paint holding expires → white flash or unstyled layout

When a user clicks a link in an MPA, the browser holds the old frame on screen until the new document is ready to paint. During TTFB, the old page is a frozen screenshot—users can't type in a search box, scroll a sidebar, or see a loading skeleton in the target area.

Problem 2: Full-Document Swap Wipes State

  • Input & focus lost — typing in a search/filter box resets mid-keystroke
  • Scroll & media reset — sidebar scroll position jumps; persistent players stop
  • Redundant work — identical <head>, navbars, and scripts are torn down and re-parsed

Even with cross-document View Transitions, a full MPA navigation replaces the entire Window and Document. Any uncommitted input state, keyboard focus, or scroll position in shared layout chrome is destroyed.

Problem 3: Cold Starts & Prerender Limits

  • Cold starts (bookmarks, omnibox, chat links) have no SPA router in memory
  • Full-page prerendering (Speculation Rules) is too heavy to run on every link
  • Prerendering /item/1 doesn't help when the user clicks /item/2

Speculative prerendering works well for high-probability next pages, but you can't prerender 50 product links on a grid. What those 50 links share is a common shell (/item/:id) that could be cached once and reused instantly.

Proposal: Progressive Shells

<head>
  <meta name="shell" content="name=store, revision=v1,
                              pattern=/item/:id, upgrade=always">
</head>
<body>
  <header><input type="search"></header>
  <main><?start name="item">Loading item...<?end></main>
  <?shellboundary name="store">
  <template for="item"><h1>Shoes</h1></template>
</body>

A single HTML document declares its shell metadata in <head>, marks dynamic slots with <?start>/<?end>, places <?shellboundary> at the end of the shell, and streams <template for> patches after the boundary.

One HTML File, Two Superpowers

1. Instant Cold Start

Browser paints cached shell for /item/:id at 0ms, then streams patches after <?shellboundary>.

2. Navigation Upgrade

Current page stays live; browser skips pre-boundary bytes and streams patches in place.

Request header: Sec-Active-Shell: name="store"; rev="v1"

Static servers and CDNs can serve the exact same full HTML file—the browser automatically skips bytes before <?shellboundary> when upgrading or using a cached shell. Dynamic servers can inspect Sec-Active-Shell and omit the shell bytes to save bandwidth.

Alt 1: Two-Phase View Transitions (deferPageSwap)

  • Keeps the old page interactive while the new page loads in the background
  • Still swaps the Document — wipes input text, focus, and sidebar state
  • Old page must guess what loading UI the destination URL needs
  • Does not help cold starts from omnibox or external links

Two-phase view transitions (deferPageSwap) delay the swap so the old page can show a spinner, but when the swap finally happens it still destroys the DOM (breaking active typing/focus), and the source page has to know how to render the destination's loading skeleton.

Alt 2: Pre-rendered Skeleton Documents

  • Idea: prerender a lightweight skeleton Document, then swap in the real Document
  • The double-swap trap: if the user types or scrolls while the skeleton is visible, swapping the real Document wipes their interaction!
  • Progressive shells patch into the same Document — state is never lost

If a cached skeleton is a separate Document from the network response, any user interaction during the skeleton phase (typing into the search bar, scrolling) is lost when the network Document replaces it. Because Progressive Shells stream patches into the already-live shell Document, state is preserved seamlessly.

Alt 3: HTTP Content Negotiation vs. <?shellboundary>

  • Why not rely purely on Accept: text/html+fragment / Vary headers?
  • CDN & static host fragility — misconfigured caches serve raw fragments as full pages
  • In-band <?shellboundary> lets one static HTML file serve cold loads, shell caching, and navigation upgrades

In-band <?shellboundary> means static sites and CDN-cached pages work out of the box without Vary header cache fragmentation, while dynamic servers can still optionally strip the shell prefix when Sec-Active-Shell matches.

Alt 4: DOM Preserve / Morphing (<header preserve>)

  • Idea: send full HTML on every navigation and keep elements marked preserve
  • Forces browser to re-download, re-parse, and diff the entire shell every time
  • Complex edge cases when <head>, stylesheets, or scripts differ
  • Explicit name + revision + <?shellboundary> is deterministic and fast

DOM morphing or preserve attributes require parsing the whole document and reconciling trees. With an explicit shell revision and boundary, the browser verifies compatibility in <head> and jumps straight to the streaming patches.

Alt 5: Service Worker HTML Stitching

  • Service Workers can concatenate a cached shell stream + network body stream
  • Still triggers a full MPA reload on navigation — no in-place SPA upgrade
  • Requires JS Service Worker registration, lifecycle management, and boot latency

Service Worker stream stitching helped cold loads in PWAs, but every link click was still a full browser navigation that destroyed DOM state. Native progressive shells handle both cached cold starts and in-place navigation upgrades declaratively.

Security & Open Questions

  • Path-prefix scoping (like Service Workers) + strict CSP / COOP / COEP match
  • Any revision or policy mismatch falls back cleanly to a normal MPA load
  • Discussion: Navigation API integration, script deferral, and cache lifetime

Invite feedback on the <meta name="shell"> syntax, URLPattern scoping rules, and how navigation upgrades should interact with the Navigation API (NavigateEvent) and View Transitions.
