Progressive Shells

Instant, seamless navigations — MPA or SPA

Explainer: https://github.com/WICG/declarative-partial-updates/blob/main/progressive-shell-explainer.md. Traces the journey from two-phase view transitions and declarative skeletons to progressive shells.

We Want Navigations to Be:

  • Instant — no waiting
  • Seamless — no uncanny valley moments or state reset

We Want This For:

  • Same-origin
  • Cross-origin
  • Cold starts

What we want from navigation on the web: instant response (even on cold starts and cross-origin links) and seamless continuity (no state reset).

Navigation Today

  • MPA: State resets, paint-freeze
  • SPA: Long cold-start or pre-hydration uncanny valley
  • Prerendering: Big RAM budget "just in case"

Today users pay in one of three ways: MPAs freeze during TTFB and reset state on swap; SPAs pay a long cold-start or sit in a pre-hydration uncanny valley; and full-page prerendering requires a big RAM budget "just in case".

1a. Two-Phase VT: Imperative (deferPageSwap)

navigation.addEventListener("navigate", event => { if (!event.destination.ready) { event.deferPageSwap({ historyChange: "immediate", async handler(controller) { const vt = document.startViewTransition(() => showPreview()); controller.addRestoreCallback(() => hidePreview()); return vt.finished; } }); } });
  • Delays cross-document page swap while the old page animates to a preview state

Imperative two-phase View Transitions add navigateEvent.deferPageSwap({ historyChange, handler }). When the destination isn't already ready, the outgoing page can run a same-document View Transition into a preview/loading state, register a BFCache/abort restore callback, and hold the cross-document page swap until the transition finishes.

1b. Two-Phase VT: Declarative (preview)

@view-transition { preview: always; } @navigation (phase: preview) { #skeleton { display: block; } } :active-view-transition-types(-ua-to-preview) { .thumbnail { view-transition-name: thumb-to-hero; } }
  • CSS-driven intermediate preview state between link click and page swap

Declarative two-phase View Transitions use @view-transition { preview: always; }, @navigation (phase: preview), and UA view-transition types (-ua-to-preview, -ua-from-preview) so the outgoing page transitions into a preview state without manual JS or BFCache cleanup callbacks.

Two-Phase VT: Why Not

  • Final swap still wipes input, focus & scroll
  • Old page must know destination UI
  • No cold-start or cross-origin win

Whether imperative or declarative, two-phase View Transitions happen on the old Document. The old page has to know how to render the destination's preview UI, it cannot run on cold starts or cross-origin navigations, and when the new Document finally swaps in, any state or input from the preview phase is wiped out.

2. Declarative Skeleton Documents

<link rel="skeleton" href="/item-skeleton.html" pattern="/item/:id">
  • Cache a separate skeleton Document per route
  • Swap to Skeleton Doc at 0ms, then to Real Doc
  • Destination owns UI; works on cold starts

Declarative Skeleton Documents flip ownership to the destination route: the browser caches a lightweight skeleton Document for a URL pattern, swaps to it at 0ms when navigation starts (even from the omnibox or cross-origin), and then swaps to the real Document when it finishes loading.

Declarative Skeletons: Why Not

  • Second swap wipes focus, scroll & typing
  • Making skeleton inert feels broken

Pre-rendering a reusable skeleton Document solves cold starts and lets the destination route define its own skeleton. But it introduces a double-swap trap: the user sees an interactive-looking skeleton at 0ms, starts typing in the search bar or scrolling, and 300ms later the real Document swaps in and wipes their interaction!

The Insight: Don't Swap the Skeleton

  • Skeleton and final page are the same Document
  • Paint shell at 0ms → stream <template for> patches

Instead of two separate Documents (skeleton + full page), a Progressive Shell is a single HTML document split by a boundary marker: the shell before the boundary, and streaming <template for> patches after the boundary.

Proposal: Progressive Shells

<head> <meta name="shell" content="name=store, revision=v1, pattern=/item/:id, upgrade=always"> </head> <body> <header><input type="search"></header> <main><?start name="item">Loading...<?end></main> <?shellboundary name="store"> <template for="item"><h1>Shoes</h1></template> </body>

One standard HTML file works everywhere: on first visit it streams normally and caches the shell prefix up to <?shellboundary>. On future visits, the shell paints at 0ms and the network response streams patches into the live Document.

One HTML File, Two Ways to Navigate

1. Instant Shell

Paint cached shell at 0ms → stream patches into the same Document.

2. Navigation Upgrade

Keep current Document live → skip shell prefix & patch in place.

Whether navigating from outside (cold start / cross-shell) or between two URLs sharing the same shell (/item/1 -> /item/2), the user gets a 0ms response and zero state loss because the Document is never swapped out after the shell is shown.

Why Not Service Worker + <template for>?

See Jake Archibald's 2016 – the year of web streams

// SW stitches cached shell + network patch stream: event.respondWith(new Response(concatStreams(cachedShell, fetch(patchUrl))));
  • No warm upgrade: Still swaps Document (or needs a separate JS router)
  • Premature 200 OK: Commits status & CSP before network responds (breaks 404, 302, version mismatch)
  • SW boot tax: Waking SW costs 50–150ms+ on cold start (Static Routing can't stitch streams)
  • Split endpoints: Needs separate fragment responses or JS stream slicing

With <template for>, a Service Worker can stitch a cached shell stream and a network patch stream into a single Document on cold start. However: (1) SW sits below navigation commit so it cannot upgrade warm navigations in place without a separate client-side JS router; (2) respondWith(new Response(stream)) must commit a 200 status and CSP headers before the network responds, breaking redirects, 404/500s, and shell version checks; (3) waking a sleeping SW adds 50-150ms+ on cold starts (and Static Routing can't concatenate cache + network); and (4) it requires separate fragment endpoints instead of one self-contained HTML file.

Other Alternatives: Why Not

  • HTTP content negotiation (Vary): Fragile on CDNs & static hosts
  • DOM morphing (preserve): Re-parses & diffs the entire shell on every navigation

Static servers can serve the exact same file while dynamic servers can inspect Sec-Active-Shell to omit the shell bytes and save bandwidth.

Security & Discussion

  • Security: Path-prefix scoping + CSP / COOP / COEP match (mismatch → MPA fallback)
  • Session history: Back/Forward & BFCache across upgraded navigations
  • Analytics & Web Vitals: Hard vs. soft navigation reporting
  • Flash of wrong user state: Auth / personalization drift in cached shells
  • Integration: Navigation API & View Transitions
