Speed vs. Smoothness in Navigation

  1. Respond at 0ms — instant shell
  2. Stay interactive — no frozen frame during TTFB
  3. Keep user state — preserve typing, focus, and scroll

Without prerendering 50 full pages or forcing “everything is JS.”

For better and for worse, many sites adopt an SPA architecture just to control their loading sequence and avoid a flash or frozen screen between pages. How do we let developers balance speed and smoothness—without forcing them into "everything is JS" or prerendering 50 full pages?

1. Two-Phase View Transitions

navigation.addEventListener("navigate", e => { e.deferPageSwap(); // or declarative intermediate VT document.startViewTransition(() => showLoadingState()); });
  • What it is: Old page transitions to an intermediate loading state (via deferPageSwap() or declarative VT) until the new page is ready
  • Why not enough:
    • Final Document swap still wipes input, focus & scroll
    • Source page must know destination UI; no cold-start win

Two-phase View Transitions (both programmatic deferPageSwap() and declarative intermediate View Transitions) let the outgoing page stay live during TTFB and animate to a loading state before the cross-document VT swap. But when the new Document arrives, the final Document swap still destroys any input focus or text typed during the wait, and it can't help cold starts or cross-origin navigations.

2. Declarative Skeleton Documents

<!-- Cached skeleton.html shown at 0ms, replaced when item.html loads --> <link rel="skeleton" href="/item-skeleton.html" pattern="/item/:id">
  • What it is: Cache a separate skeleton Document for a route pattern; swap to it at 0ms, then swap to the real Document on load
  • Why not enough:
    • Fixes cold starts; destination owns its skeleton
    • Double-Swap Trap: Skeleton Doc → Real Doc wipes state

Pre-rendering a reusable skeleton Document solves cold starts and lets the destination route define its own skeleton. But it introduces a double-swap trap: the user sees an interactive-looking skeleton at 0ms, starts typing in the search bar or scrolling, and 300ms later the real Document swaps in and wipes their interaction!

The Insight: Don't Swap the Skeleton

  • Skeleton and final page are the same Document
  • Paint shell at 0ms → stream <template for> patches

Instead of two separate Documents (skeleton + full page), a Progressive Shell is a single HTML document split by a boundary marker: the shell before the boundary, and streaming <template for> patches after the boundary.

Proposal: Progressive Shells

<head> <meta name="shell" content="name=store, revision=v1, pattern=/item/:id, upgrade=always"> </head> <body> <header><input type="search"></header> <main><?start name="item">Loading...<?end></main> <?shellboundary name="store"> <template for="item"><h1>Shoes</h1></template> </body>

One standard HTML file works everywhere: on first visit it streams normally and caches the shell prefix up to <?shellboundary>. On future visits, the shell paints at 0ms and the network response streams patches into the live Document.

One HTML File, Two Ways to Navigate

1. Instant Shell

Paint cached shell at 0ms → stream patches into the same Document.

2. Navigation Upgrade

Keep current Document live → skip shell prefix & patch in place.

Whether navigating from outside (cold start / cross-shell) or between two URLs sharing the same shell (/item/1 -> /item/2), the user gets a 0ms response and zero state loss because the Document is never swapped out after the shell is shown.

Why In-Band <?shellboundary>?

  • vs. Vary header: Works on static hosts & CDNs
  • vs. DOM morphing (preserve): No full-shell re-parse or diff
  • vs. Service Worker stitching: Works before SW activation; upgrades in place

Static servers can serve the exact same file while dynamic servers can inspect Sec-Active-Shell to omit the shell bytes and save bandwidth.

Security & Discussion

  • Path-prefix scoping + strict CSP / COOP / COEP match
  • Any mismatch → clean fallback to normal MPA navigation
