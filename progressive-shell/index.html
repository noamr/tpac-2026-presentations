The MPA vs. SPA Trade-off

MPAs

  • Simple, zero router JS
  • Frozen screen on click
  • Full state loss on swap

SPAs

  • Instant feedback & state
  • Heavy JS bundle tax
  • Slow cold starts

Authors have to choose between simple server-rendered MPAs (which freeze during navigation and wipe DOM state on swap) and heavy JS SPAs (just to keep a header, search input, or sidebar alive across clicks).

Three Broken Moments in MPAs

  1. Frozen Frame — paint holding freezes the old page until TTFB
  2. State Loss — full-document swap wipes focus, inputs, and scroll
  3. Prerender Limits — you can't prerender 50 product links on a grid

1. Paint holding makes the old page look interactive while ignoring typing and scrolling. 2. When the swap happens, any active input or sidebar state is destroyed. 3. Speculation Rules can't prerender dozens of item links, even though they all share the exact same shell.

Proposal: Progressive Shells

<head>
  <meta name="shell" content="name=store, revision=v1,
                              pattern=/item/:id, upgrade=always">
</head>
<body>
  <header><input type="search"></header>
  <main><?start name="item">Loading...<?end></main>
  <?shellboundary name="store">
  <template for="item"><h1>Shoes</h1></template>
</body>

A single HTML file declares its shell metadata in <head>, marks dynamic slots with <?start>/<?end>, places <?shellboundary> at the end of the shell, and streams <template for> patches after the boundary.

One File, Two Superpowers

1. Instant Cold Start

Paint cached shell at 0ms → stream patches after <?shellboundary>.

2. Navigation Upgrade

Keep current page live → skip pre-boundary bytes & patch in place.

Static hosts can serve the exact same full HTML file; the browser skips bytes before <?shellboundary> when upgrading or using a cached shell. Dynamic servers can inspect Sec-Active-Shell and omit the shell prefix to save bandwidth.

Alternatives Considered (1/2)

  • Two-Phase View Transitions (deferPageSwap)
    • Still swaps the Document → wipes input, focus, and state
  • Pre-rendered Skeleton Documents
    • Double-swap trap: typing in the skeleton is wiped when the real Document swaps in
  • DOM preserve / Morphing
    • Re-downloads, re-parses, and diffs the entire shell on every click

deferPageSwap and pre-rendered skeleton Documents both suffer from a fatal flaw: they still perform a full Document swap when the network response arrives, destroying any typing or scrolling the user did while waiting. Progressive Shells patch into the same live Document.

Alternatives Considered (2/2)

  • HTTP Content Negotiation (Accept: text/html+fragment)
    • Breaks static hosts; fragile CDN Vary caching
  • Service Worker Stream Stitching
    • Requires JS SW boot; link clicks still do a full MPA reload

In-band <?shellboundary> works on any static host and upgrades gracefully.

Relying purely on HTTP headers breaks static file servers and risks CDN cache poisoning if Vary is misconfigured. Service Worker stitching still triggers full MPA page reloads on navigation. In-band <?shellboundary> works everywhere.
