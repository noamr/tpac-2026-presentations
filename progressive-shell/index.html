The Goal: Instant, Seamless Navigations

Whether MPA or SPA, every navigation should:

  1. Respond at 0ms — instant shell / skeleton on click or cold start
  2. Stay interactive — no “frozen frame” while waiting for TTFB
  3. Preserve state — never wipe active typing, focus, or scroll

And you can't full-prerender 50 product links on a grid.

Today MPAs freeze the screen (paint holding) until TTFB and then wipe all DOM state on swap. SPAs pay a heavy JS router/hydration tax and still have slow cold starts. Full-page Speculation Rules can't prerender 50 links on a page. How do we make every navigation instant and seamless?

Approach 1: Two-Phase View Transitions (deferPageSwap)

Idea: Keep the old page interactive & transition to a loading state while the new Document loads in the background.

  • ❌ Still swaps the Document at the end — wipes any typing or scroll done while waiting
  • ❌ Source page must know destination UI
  • ❌ Doesn't help cold starts

With deferPageSwap, the old page stays live during TTFB and can animate to an intermediate state. But when the new Document finally arrives, the browser still swaps Documents—destroying any input focus or search text the user typed during the wait. Plus, every source page has to know how to render the destination's loading skeleton.

Approach 2: Declarative Skeleton Documents

Idea: Pre-cache a lightweight skeleton Document for /item/:id → swap to skeleton at 0ms → swap to real Document when loaded.

  • ✅ Fixes cold starts & destination owns its skeleton
  • ❌ The Double-Swap Trap: swapping from the skeleton Document to the real Document still wipes user input, focus, and scroll!

Pre-rendering a reusable skeleton Document solves cold starts and lets the destination route define its own skeleton. But it introduces a double-swap trap: the user sees an interactive-looking skeleton at 0ms, starts typing in the search bar or scrolling, and 300ms later the real Document swaps in and wipes their interaction!

The Insight: Don't Swap Out the Skeleton!

  • Why load a skeleton Document only to throw it away 200ms later?
  • Make the skeleton and the final page the same Document
  • Paint the shell at 0ms → stream the real content into it via <template for>

Instead of two separate Documents (skeleton + full page), a Progressive Shell is a single HTML document split by a boundary marker: the shell before the boundary, and streaming <template for> patches after the boundary.

Proposal: Progressive Shells

<head>
  <meta name="shell" content="name=store, revision=v1,
                              pattern=/item/:id, upgrade=always">
</head>
<body>
  <header><input type="search"></header>
  <main><?start name="item">Loading...<?end></main>
  <?shellboundary name="store">
  <template for="item"><h1>Shoes</h1></template>
</body>

One standard HTML file works everywhere: on first visit it streams normally and caches the shell prefix up to <?shellboundary>. On future visits, the shell paints at 0ms and the network response streams patches into the live Document.

One File, Both MPA & SPA Superpowers

1. Instant Shell (Cold / Cross-Shell)

Paint cached shell at 0ms → stream post-boundary patches into the same Document.

2. Navigation Upgrade (Same Shell)

Keep current Document live → skip pre-boundary bytes & patch in place.

Whether navigating from outside (cold start / cross-shell) or between two URLs sharing the same shell (/item/1 -> /item/2), the user gets a 0ms response and zero state loss because the Document is never swapped out after the shell is shown.

Why In-Band <?shellboundary>?

  • vs. HTTP Content Negotiation (Vary): Works on static hosts & CDNs without cache fragmentation
  • vs. DOM Morphing (preserve): Doesn't re-parse and diff the whole shell on every click
  • vs. Service Worker Stitching: Zero JS boot tax; supports in-place navigation upgrades

Static servers can serve the exact same file while dynamic servers can inspect Sec-Active-Shell to omit the shell bytes and save bandwidth.

Security & Discussion

  • Path-prefix scoping + strict CSP / COOP / COEP match
  • Any mismatch → clean fallback to normal MPA navigation
