Silent Focus Loss

deleteButton.focus(); deleteButton.remove(); // document.activeElement === document.body (0 events fired!)
  • activeElement resets to document.body with zero events
  • Focus traps, roving-tabindex widgets, shortcuts & AT (aria#2920) break

Per HTML's node-remove focus fixup rule, removing the focused element resets focus to the viewport without firing blur or focusout. Gecko and WebKit fire nothing; Blink has been stuck with a legacy synchronous blur because libraries have no alternative (whatwg/html#12842).

What We Force Libraries to Ship Today

MutationObserver on body

Radix UI, focus-trap

  • Runs on every single DOM edit
  • Breaks inside Shadow DOM

setInterval Polling

Material UI, Tridactyl

  • Polls activeElement every 200ms
  • Wastes CPU & lags

When a platform signal is missing, libraries end up inventing bent-backwards workarounds: either observing every single childList mutation on document.body or polling document.activeElement on a 200ms timer just to notice that focus silently dropped to body.

Proposal: focusreset on Document

document.addEventListener("focusreset", () => { if (dialog.open && !dialog.contains(document.activeElement)) { dialog.focus(); } });
  • Fires in the mutation observer microtask
  • Plain Event — no detached node reference

Fires at Document at the end of the mutation observer microtask (after MutationObserver callbacks and slotchange). Omitting relatedTarget avoids keeping detached DOM subtrees alive and preserves closed Shadow DOM encapsulation.

Auto-Cancellation

item.remove(); nextItem?.focus(); // cancels focusreset if nextItem exists; fires if list is now empty!
  • Only fires for unhandled focus loss
  • Fires on the affected Document (iframe's contentDocument, or parent if <iframe> removed)
  • moveBefore() preserves focus → no focusreset

If script explicitly moves focus before the microtask runs (via .focus(), showModal(), or autofocus), the pending focusreset is cancelled so fallback handlers don't override it. If both an iframe button and the iframe itself are removed, focusreset only fires on the parent Document.

Timing: Microtask vs. Rendering

  • display: none: Resets activeElement & fires blur after layout
  • node.remove(): Resets activeElement synchronously; focusreset fires in the MO microtask (catches rAF / ResizeObserver removals too)

Step 17 of update-the-rendering is for style changes (display:none) and updates activeElement + fires blur together. On DOM removal, activeElement is already reset synchronously; firing focusreset in the MutationObserver microtask keeps it in sync with activeElement and handles removals during rAF/ResizeObserver.

Why Not…

  • Sync blur: Re-entrancy hazard
  • Async blur on ancestor: Ancestor was never focused
  • FocusEvent.relatedTarget (removed node): Leaks detached & closed Shadow DOM

Synchronous events during DOM removal are unsafe. Firing blur on a parent that was never focused is semantically wrong and breaks if ancestors are reparented. Omitting relatedTarget avoids detached DOM leaks and preserves closed Shadow DOM encapsulation.

Status & Discussion

  • HTML PR #13050 · DOM PR #1512 · WPT #63595
  • Migration path to deprecate Blink's sync blur (whatwg/html#12842) & w3c/aria#2920
  • Open questions:
    • Microtask vs. rendering timing?
    • Also fire on style/attribute focus fixup (display: none, inert, disabled)?
    • Document-only vs. ShadowRoot (or is focusout sufficient)?

Participate: focusreset-explainer.md · whatwg/html#13050

Since libraries like Radix and MUI already maintain fallbacks for Gecko and WebKit, shipping focusreset gives them a clean migration path so Blink can finally deprecate its legacy synchronous blur. Open questions for the room: (1) microtask vs. update-the-rendering timing, (2) whether focusreset should also fire on style/attribute focus fixups like display:none/inert/disabled (even though those already fire blur/focusout, a single focusreset handler could catch all involuntary resets to body), and (3) whether Document-only is sufficient.
