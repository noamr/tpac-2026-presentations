The Silent Focus Loss Problem

When a focused element (or its ancestor) is removed from the DOM:

  • HTML's node-remove focus fixup rule resets focus to document.body
  • No blur or focusout event is fired per spec
  • Keyboard & assistive tech users silently lose their place; modal focus traps break

Deleting a todo item, closing a popover, or re-rendering a component subtree silently drops focus to document.body. Gecko and WebKit fire nothing; Blink fires a legacy synchronous blur that violates the spec and causes re-entrancy bugs (whatwg/html#12842).

Painful Workarounds Today

MutationObserver on body

Used by Radix UI & focus-trap.

  • Fires on every DOM mutation
  • Fails across Shadow DOM
  • Misfires on unrelated edits

setInterval Polling

Used by Material UI & Tridactyl.

  • Polls activeElement every 200ms
  • Unnecessary CPU wakeups
  • 200ms window of escaped focus

Every major accessible component library has had to invent brittle hacks—either observing the entire document tree for childList mutations or polling document.activeElement on a timer.

Proposal: focusreset on Document

document.addEventListener("focusreset", () => {
  if (modal.open && !modal.contains(document.activeElement)) {
    modal.querySelector("button")?.focus();
  }
});
  • Dispatched on Document (document.onfocusreset)
  • Plain Event — non-bubbling, non-cancelable, no relatedTarget

Omitting relatedTarget ensures the removed DOM subtree can be garbage-collected immediately and avoids leaking nodes across closed Shadow DOM boundaries.

Microtask Timing & Auto-Cancellation

deleteButton.remove();
nextItemButton.focus(); // Explicitly restores focus
// -> focusreset is automatically cancelled!
  • Fires at the end of the mutation observer microtask (before rendering)
  • Auto-cancelled if focus is moved before dispatch (.focus(), showModal(), autofocus)

Because components often remove a node and immediately focus its replacement on the next line, queuing focusreset for the microtask checkpoint and cancelling it when focus is restored prevents false alarms. Microtask timing also ensures removals inside rAF or ResizeObserver are caught before the frame paints.

Nested <iframe>s & moveBefore()

// Focused button inside an iframe:
iframeButton.remove();
iframe.remove();
// -> Fires focusreset ONLY on the parent Document!
  • Document focus is checked both on removal and at microtask dispatch
  • State-preserving moveBefore() keeps focus intact → no focusreset

Using HTML's "has focus steps" at both removal time and microtask dispatch time naturally suppresses redundant events in detached child iframes while notifying the still-focused parent document.

Alternatives Considered

  • Synchronous blur on removal — script re-entrancy hazard mid-DOM-removal
  • Async blur / focusout on ancestor — semantically wrong & arbitrary under reparenting
  • Rendering-step timing — misses removals inside requestAnimationFrame / ResizeObserver
  • Exposing relatedTarget — retains detached DOM trees & leaks closed Shadow DOM

A dedicated event on Document at the microtask checkpoint avoids re-entrancy, avoids overloading blur/focusout semantics, and gives libraries a zero-overhead replacement for polling and MutationObservers.
