What the Parser Knows (and the DOM Forgets)

  • Is this element finished parsing? (open vs. closed tag)
  • <template>s that don't attach to the DOM (shadowrootmode, for)
  • Which container triggered this parse? (innerHTML, setHTML, streamHTML, patch)

The HTML parser tracks the stack of open elements, processes special <template> elements that are consumed by the parser without ever attaching to the DOM (Declarative Shadow DOM and <template for>), and knows the fragment context root—none of which is visible to MutationObserver today.

Why It Hurts Today

  • SSR & Hydration: Components hydrate on start tag before children exist
  • <template shadowrootmode> & <template for>: Never attach to the DOM

SSR frameworks, custom elements, and hydration libraries cannot tell when a server-streamed element's children have finished parsing (whatwg/dom#898, w3c/webcomponents#809). And non-attaching <template> elements (<template shadowrootmode> and <template for>) never enter addedNodes, so observers can't attribute mutations to a patch, know when a patch finishes, or detect when a patch's target was missing.

What Developers Are Saying

“MutationObserver sees the resulting DOM changes, not parser intent or terminal state… Knowing which patch caused a mutation (and how it resolved) is way more useful than just knowing ‘the DOM changed.’”

— @callie-openai (OpenAI, WICG/declarative-partial-updates#110)

“There is no way to know within connectedCallback if the node has finished parsing its children or not.”

— @WebReflection (w3c/webcomponents#809, 100+ 👍)

In WICG/declarative-partial-updates#110, OpenAI described building a streaming UI prototype where they had to build a custom document-level patch feed because MutationObserver couldn't separate parser-owned patch mutations from hydration or client UI updates, nor detect missing targets or stream EOF aborts. Meanwhile w3c/webcomponents#809 and whatwg/dom#898 have asked for parser completion state for years.

The Footgun Dilemma: Parsing vs. Dynamic DOM

“If we expose a parser-completion hook, developers will rely on it and forget to handle dynamic DOM updates.”

  • With an isolated parsedCallback, that's a real risk
  • Put the footgun in plain sight: On MutationRecord, parser state sits right next to addedNodes — parsing is part of the story, not the whole story

As I wrote in "Incremental HTML Rendering & The Footgun Fallacy", focusing on misuse too much can block useful primitives or push developers into bent-backwards workarounds. Sometimes the best way to prevent a footgun is to put it in plain sight: putting parser state directly on MutationRecord—right alongside addedNodes and removedNodes—reminds developers that parsing is just one source of DOM mutations.

Proposal: { parser: true }

observer.observe(document, { childList: true, subtree: true, parser: true });
  • node.isParsing & record.parsedElements
  • record.templateStatus & record.templateAttributes
  • record.parserContextElement

Opt-in via parser: true on MutationObserverInit. Parser state arrives in the exact same MutationRecords as childList and characterData mutations, and never coalesces parser-patch mutations with unrelated JS DOM edits.

Knowing When Elements Finish: parsedElements

// Chunk 1: "<my-card><h2>Title</h2>" -> myCard.isParsing === true // Chunk 2: "<p>Body</p></my-card>" -> myCard.isParsing === false

parsedElements lists elements that popped off the parser's stack of open elements. Whenever possible, it is coalesced onto existing childList records so no extra MutationRecords are allocated.

Observing Non-Attaching <template>s

for (const r of records) { if (r.templateStatus === "start") { // DSD attached or <template for> patch started! console.log(r.templateAttributes.getNamedItem("for")); } }
  • templateStatus: "start" → "update" → "end" | "abort"

Tracks both <template shadowrootmode> and <template for> (including characterData streaming, missing targets, and EOF aborts). templateAttributes is a read-only NamedNodeMap that preserves object identity across all chunks of a single template.

Alternatives Considered

  • New record type ("parsedElement") — 2× record allocations
  • DOM events (parseend / patch) — interrupts parser / event storm
  • Separate PatchObserver — splits parser flow from dynamic DOM mutations

As discussed in #110, synchronous events pause the parser, and a separate observer loses ordering with ordinary DOM mutations. Enriched MutationRecords deliver microtask-batched metadata in lockstep with DOM changes.

Discussion: Finding the Sweet Spot

  • How do we support SSR & streaming HTML without pretending parsing is the only way the DOM changes?
  • Does putting { parser: true } on MutationObserver + node.isParsing strike the right balance?

Open discussion on how { parser: true } and node.isParsing hit the balance between ergonomic server-driven/streaming HTML observation and reminding developers that DOM trees also mutate dynamically after parsing.
