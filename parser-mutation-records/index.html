Use Case 1: Streaming Children (#809, dom#662)

<!-- Chunk 1 --> <s-select><s-option>A</s-option> <!-- Chunk 2 --> <s-option>B</s-option></s-select>
  • addedNodes fires on the start tag — across network chunks, children are incomplete
  • Hits custom elements validating/slotting children (<s-select>), inline code blocks, and streaming MPA→SPA updates (dom#1116)
  • Today's workaround (html-parsed-element, writable-dom): per-element observers + ancestor nextSibling walks (100ms+ main-thread cost)

In WICG/webcomponents#809, whatwg/dom#662, and whatwg/dom#1116, developers building custom elements (like Shopify's <s-select> validating <s-option> children, data tables, or Svelte's light-DOM slots) and streaming HTML swaps hit the same wall: addedNodes and connectedCallback fire on the opening tag, when the parser may yield mid-element across network chunks. Libraries like html-parsed-element and Marko's writable-dom have to walk ancestor nextSibling chains on every mutation, burning 100ms+ of main-thread time.

Use Case 2: Streaming Patches (#110, html#13008)

<template for="results" data-turn="3"> <p>Streamed response...</p> </template>
  • <template for> is consumed by the parser and never enters addedNodes
  • Streaming UIs (e.g., OpenAI's prototype in #110) need attribution & error control:
    • Which patch caused this mutation (e.g. data-turn="3")?
    • Did the patch finish ("end") or fail ("abort" on truncated stream / missing target)?

In WICG/declarative-partial-updates#110 (filed by OpenAI) and whatwg/html#13008, streaming applications using <template for> need to correlate DOM mutations with the initiating patch, read metadata attributes off the template, and know whether a patch finished cleanly or aborted due to network truncation or a missing target. Without parser reflection, apps must build a parallel client-side patch feed.

Use Case 3: Declarative Shadow DOM (dom#1287)

<my-card> <template shadowrootmode="open"> <unregistered-child></unregistered-child> </template> </my-card>
  • Component autoloaders & polyfills (e.g. Web Awesome) need to observe inside shadow roots
  • Monkey-patching attachShadow() misses <template shadowrootmode> completely
  • Parser consumes the <template> with zero MutationRecords on the host

In whatwg/dom#1287 and #1439, component autoloaders and polyfills need to discover shadow roots as they attach. Today they monkey-patch Element.prototype.attachShadow(), which completely misses Declarative Shadow DOM because the parser consumes <template shadowrootmode> without queueing any MutationRecord on the host.

Parsing vs. Dynamic DOM

“If we expose a parser-completion hook, developers will rely on it and forget to handle dynamic DOM updates.”

  • An isolated parsedCallback hides dynamic updates
  • On MutationRecord, parser state sits right next to addedNodes

As I wrote in "Incremental HTML Rendering & The Footgun Fallacy", focusing on misuse too much can block useful primitives or push developers into bent-backwards workarounds. Sometimes the best way to prevent a footgun is to put it in plain sight: putting parser state directly on MutationRecord—right alongside addedNodes and removedNodes—reminds developers that parsing is just one source of DOM mutations.

Proposal: { parser: true }

observer.observe(document, { childList: true, subtree: true, parser: true });
  • node.isParsing & record.parsedElements
  • record.templateStatus & record.templateAttributes
  • record.parserContextElement

Opt-in via parser: true on MutationObserverInit. Parser state arrives in the exact same MutationRecords as childList and characterData mutations, and never coalesces parser-patch mutations with unrelated JS DOM edits.

parsedElements & isParsing

// Chunk 1: "<my-card><h2>Title</h2>" // addedNodes: [my-card, h2], parsedElements: [h2] // myCard.isParsing === true // Chunk 2: "<p>Body</p></my-card>" // addedNodes: [p], parsedElements: [p, my-card] // myCard.isParsing === false
  • parsedElements coalesces onto the same childList record

parsedElements lists elements that popped off the parser's stack of open elements. Whenever possible, it is coalesced onto existing childList records so no extra MutationRecords are allocated.

Non-Attaching <template>s

for (const r of records) { if (r.templateStatus === "start") { console.log(r.templateAttributes.getNamedItem("for")); } }
  • templateStatus: "start" → "update" → "end" | "abort"

Tracks both <template shadowrootmode> and <template for> (including characterData streaming, missing targets, and EOF aborts). templateAttributes is a read-only NamedNodeMap that preserves object identity across all chunks of a single template.

Alternatives Considered

  • New record type ("parsedElement"): 2× record allocations
  • DOM events (parseend / patch): Interrupts parser
  • Separate PatchObserver: Splits parser from dynamic DOM

As discussed in #110, synchronous events pause the parser, and a separate observer loses ordering with ordinary DOM mutations. Enriched MutationRecords deliver microtask-batched metadata in lockstep with DOM changes.
