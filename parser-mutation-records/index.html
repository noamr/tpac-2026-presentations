Parser-Aware MutationObserver

Bridging the HTML parser and the DOM

Explainer: https://github.com/WICG/declarative-partial-updates/blob/main/parser-mutation-records-explainer.md. Proposes extending MutationObserver with { parser: true } and Node/ShadowRoot with isParsing.

What the Parser Knows (and the DOM Forgets)

  • Is this element finished parsing? (open vs. closed tag)
  • Did a <template> just run? (shadowrootmode, for)
  • Which container triggered this parse? (innerHTML, setHTML, streamHTML, patch)

The HTML parser tracks the stack of open elements, consumes special <template> directives (Declarative Shadow DOM and <template for>), and knows the fragment context root for innerHTML, setHTML, streamHTML, and patches—none of which is visible to MutationObserver today.

Why It Hurts Today

  • addedNodes fires on the start tag — children may not exist yet
  • Declarative Shadow Roots attach silently
  • Streaming <template for> patches & streamHTML lack completion boundaries

Custom elements and hydration libraries cannot tell if an element's children have finished parsing (whatwg/dom#898, w3c/webcomponents#809); nextSibling hacks add 100ms+ latency and fail on last children. And DSD / streaming patches emit zero lifecycle records.

The Classic Objection

“If we expose a parser-completion hook, developers will rely on it and forget to handle dynamic DOM updates.”

  • True for isolated lifecycle callbacks (parsedCallback alone)
  • Our goal: Find the sweet spot — reflect the flow of HTML/server-driven UI while keeping developers aware that HTML parsing is not the whole story

In past discussions around parsedCallback (w3c/webcomponents#809), a valid concern was that authors would write components that only work when parsed from HTML and break when children are appended dynamically via JS. Putting parser state directly on MutationRecord—alongside addedNodes and removedNodes—keeps parser boundaries inside the unified DOM mutation pipeline rather than pretending parsing is the only way DOM changes happen.

Proposal: { parser: true }

observer.observe(document, {
  childList: true,
  subtree: true,
  parser: true
});
  • node.isParsing & record.parsedElements
  • record.templateStatus & record.templateAttributes
  • record.parserContextElement

Opt-in via parser: true on MutationObserverInit. Parser state arrives in the exact same MutationRecords as childList mutations, so observers naturally handle both dynamic DOM updates and chunked HTML parsing together.

Knowing When Elements Finish: parsedElements

// Chunk 1: "<my-card><h2>Title</h2>"
myCard.isParsing; // true

// Chunk 2: "<p>Body</p></my-card>"
// record.parsedElements -> [p, my-card]
myCard.isParsing; // false

parsedElements lists elements that popped off the parser's stack of open elements. Whenever possible, it is coalesced onto existing childList records so no extra MutationRecords are allocated.

Observing Consumed <template>s

for (const r of records) {
  if (r.templateStatus === "start") {
    // DSD attached or <template for> patch started!
    console.log(r.templateAttributes.getNamedItem("for"));
  }
}
  • templateStatus: "start" → "update" → "end" | "abort"

Tracks both <template shadowrootmode> and <template for>. templateAttributes is a read-only NamedNodeMap that preserves object identity across all chunks of a single template without retaining a detached DOM tree.

Alternatives Considered

  • New record type ("parsedElement") — 2× record allocations
  • DOM events (parseend) — MutationEvent storm
  • Separate PatchObserver — splits parser flow from dynamic DOM mutations

A separate PatchObserver or standalone event would isolate parser events from ordinary DOM mutations. Coalescing onto childList MutationRecords keeps zero extra allocation overhead and unifies parser + dynamic DOM observation.

Discussion: Finding the Sweet Spot

  • How do we best support HTML / server-driven UI (streaming, streamHTML, patches) without encouraging code that ignores dynamic DOM updates?
  • Is MutationObserver({ parser: true }) + node.isParsing the right primitive layer?

Open discussion on how { parser: true } and node.isParsing hit the balance between ergonomic server-driven/streaming HTML observation and reminding developers that DOM trees also mutate dynamically after parsing.
