Explainer: https://github.com/WICG/declarative-partial-updates/blob/main/parser-mutation-records-explainer.md. Proposes extending MutationObserver with { parseEnd: true, template: true } and Element/ShadowRoot with isParsing.

1. Parse End: Complete Subtrees (dom#662, wc#809)

<!-- Chunk 1 --> <s-select><s-option>A</s-option> <!-- Chunk 2 --> <s-option>B</s-option></s-select>
  • addedNodes fires on the start tag — before children finish streaming
  • Needed to evaluate code/math once (dom#1116), batch child setup (<s-select>), and animate complete subtrees (html#12200)
  • Today's ancestor-walk workarounds cost 100ms+ on the main thread

Why do developers need to know when an element finishes parsing? Three concrete cases from dom#662, dom#1116, html#12200, and webcomponents#809: evaluating text/script/config children once without chunk-split errors, validating or indexing light-DOM children (like Shopify's <s-select>), and animating streamed subtrees only once complete. Today addedNodes fires on the start tag, forcing 100ms+ ancestor-walk workarounds.

2. Patching: <template for> (#110, html#13008)

<template for="results" data-turn="3"> <p>Streamed response...</p> </template>
  • The parser consumes <template for> — it never enters the DOM
  • Attribution: Separate server patches from client edits & read data-turn="3"
  • Flow & error control: Detect patch start, end, or abort (truncated stream / missing target)

Second core use case (WICG/declarative-partial-updates#110 from OpenAI, whatwg/html#13008): attribution, flow control, and error recovery for declarative <template for> patches. Because the parser consumes <template for> without adding it to the DOM, apps cannot tell which patch caused a mutation, when a patch finishes, or when a patch aborts due to network truncation or a missing target.

Parsing vs. Dynamic DOM

“If we expose a parser-completion hook, developers will rely on it and forget to handle dynamic DOM updates.”

  • An isolated callback hides dynamic updates
  • On MutationRecord, parser state sits right next to addedNodes

As I wrote in "Incremental HTML Rendering & The Footgun Fallacy", focusing on misuse too much can block useful primitives or push developers into bent-backwards workarounds. Sometimes the best way to prevent a footgun is to put it in plain sight: putting parser state directly on MutationRecord—right alongside addedNodes and removedNodes—reminds developers that parsing is just one source of DOM mutations.

Proposal: Parser-Aware MutationObserver

observer.observe(document, { childList: true, subtree: true, parseEnd: true, template: true });
  • element.isParsing — is the parser still inside this element?
  • parseEnd: true — notify when an open element closes in a later chunk
  • template: true — expose <template for> status & attributes

Two opt-in flags on MutationObserverInit—parseEnd: true and template: true—plus element.isParsing (and record.parserContextElement for fragment parsing).

1. Parse End (parseEnd: true)

// 1. Opened & closed in the same chunk: if (!node.isParsing) setup(node); // 2. Closed in a later chunk (empty childList record): if (!r.addedNodes.length && !r.target.isParsing) { setup(r.target); }
  • Same chunk: Zero extra records — check !node.isParsing on addedNodes
  • Split across chunks: Record fires on el when </el> arrives

Because MutationObserver runs in a microtask after the chunk finishes, same-chunk elements already have isParsing === false when seen in addedNodes. Only elements still open across a chunk boundary emit an empty childList record (target === closedElement, previousSibling === el.lastChild) when their end tag arrives.

2. Patching (template: true)

const target = r.templateAttributes?.getNamedItem("for")?.value; if (target) { // r.templateStatus: "start" | "update" | "end" | "abort" }
  • templateAttributes: Read attributes from the active <template for>
  • templateStatus: "start" → "update" → "end" | "abort"

Every record produced during a patch carries templateAttributes (a read-only NamedNodeMap shared across all records of that patch) and templateStatus ("start", "update", "end", or "abort" if truncated at EOF or missing its target).

Bonus: Shadow DOM & Custom Elements

  • Declarative Shadow DOM (dom#1287): template: true also reports <template shadowrootmode> attachment & completion (for autoloaders, a11y tools, SSR)
  • Custom element reactions: Same primitives can back parsedCallback() and shadowRootAttachedCallback()

As a bonus: because <template shadowrootmode> is also a parser-consumed template, template: true solves whatwg/dom#1287 (discovering declarative shadow roots without monkey-patching attachShadow()). And for custom elements, the same underlying signals can power parsedCallback() (firing after connectedCallback() or on parse end) and shadowRootAttachedCallback().

Alternatives Considered

  • record.parsedElements NodeList: Extra list allocation; requires observing parent
  • New record type ("parseEnd"): 2× record allocations for same-chunk elements
  • DOM events / separate PatchObserver: Interrupts parser or loses DOM ordering

As discussed in #110, synchronous events pause the parser, and a separate observer loses ordering with ordinary DOM mutations. Enriched MutationRecords deliver microtask-batched metadata in lockstep with DOM changes.
