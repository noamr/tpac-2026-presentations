Explainer: https://github.com/WICG/declarative-partial-updates/blob/main/parser-mutation-records-explainer.md. Proposes extending MutationObserver with { parser: true } and Node/ShadowRoot with isParsing.

1. Acting on Complete Subtrees (dom#662, #1116, wc#809)

<!-- Chunk 1 --> <s-select><s-option>A</s-option> <!-- Chunk 2 --> <s-option>B</s-option></s-select>
  • Evaluate content once: Code blocks, math/markdown elements, or streamed scripts without chunk-split syntax errors
  • Batch child setup & validation: Validate/slot children (<s-select>) without false warnings or O(N²) re-layout per chunk
  • Animate complete subtrees: Trigger View Transitions or reveal streamed nodes without half-parsed layout shifts (html#12200)

Why do developers need to know when an element finishes parsing? Three concrete objectives from dom#662, dom#1116, html#12200, and webcomponents#809: (1) evaluating text/script/config children once without syntax errors when a network chunk splits the element; (2) validating or indexing light-DOM children (like Shopify's <s-select>) without false errors or redoing work on every chunk; and (3) animating or revealing streamed subtrees only once complete. Today addedNodes fires on the start tag, forcing 100ms+ ancestor-walk workarounds.

2. Patch Attribution & Error Control (#110, html#13008)

<template for="results" data-turn="3"> <p>Streamed response...</p> </template>
  • Attribution: Separate parser-streamed patches from client UI edits & read server metadata (data-turn="3")
  • Flow control: Know when a streamed patch starts and settles ("end") to trigger hydration or scroll behavior
  • Error recovery: Detect truncated streams or missing targets ("abort") to show retry/fallback UI

Second objective (WICG/declarative-partial-updates#110 from OpenAI, whatwg/html#13008): attribution, flow control, and error recovery for declarative <template for> patches. Because the parser consumes <template for> without adding it to the DOM, apps cannot tell which patch caused a mutation, when a patch finishes, or when a patch aborts due to network truncation or a missing target.

3. Observing Declarative Shadow DOM (dom#1287)

<my-card> <template shadowrootmode="open"> <wa-button>Lazy-loaded</wa-button> </template> </my-card>
  • Component autoloaders: Lazy-load custom element definitions (e.g. Web Awesome / Shoelace) when tags appear inside shadow trees
  • Accessibility & DOM auditing: Run live a11y checks (e.g. Accented) across open shadow roots as markup streams in
  • SSR shadow-root hydration: Know when a declarative shadow root attaches ("start") and finishes parsing ("end")

Third objective (whatwg/dom#1287): observing Declarative Shadow DOM (<template shadowrootmode>) for component autoloaders (like Web Awesome/Shoelace lazy-loading custom element definitions), live accessibility auditing tools (like Accented), and SSR hydration. Today libraries monkey-patch attachShadow(), which completely misses Declarative Shadow DOM because the parser attaches the ShadowRoot with zero MutationRecords.

Parsing vs. Dynamic DOM

“If we expose a parser-completion hook, developers will rely on it and forget to handle dynamic DOM updates.”

  • An isolated parsedCallback hides dynamic updates
  • On MutationRecord, parser state sits right next to addedNodes

As I wrote in "Incremental HTML Rendering & The Footgun Fallacy", focusing on misuse too much can block useful primitives or push developers into bent-backwards workarounds. Sometimes the best way to prevent a footgun is to put it in plain sight: putting parser state directly on MutationRecord—right alongside addedNodes and removedNodes—reminds developers that parsing is just one source of DOM mutations.

Proposal: { parser: true }

observer.observe(document, { childList: true, subtree: true, parser: true });
  • node.isParsing & record.parsedElements
  • record.templateStatus & record.templateAttributes
  • record.parserContextElement

Opt-in via parser: true on MutationObserverInit. Parser state arrives in the exact same MutationRecords as childList and characterData mutations, and never coalesces parser-patch mutations with unrelated JS DOM edits.

parsedElements & isParsing

// Chunk 1: "<my-card><h2>Title</h2>" // addedNodes: [my-card, h2], parsedElements: [h2] // myCard.isParsing === true // Chunk 2: "<p>Body</p></my-card>" // addedNodes: [p], parsedElements: [p, my-card] // myCard.isParsing === false
  • parsedElements coalesces onto the same childList record

parsedElements lists elements that popped off the parser's stack of open elements. Whenever possible, it is coalesced onto existing childList records so no extra MutationRecords are allocated.

Non-Attaching <template>s

for (const r of records) { if (r.templateStatus === "start") { console.log(r.templateAttributes.getNamedItem("for")); } }
  • templateStatus: "start" → "update" → "end" | "abort"

Tracks both <template shadowrootmode> and <template for> (including characterData streaming, missing targets, and EOF aborts). templateAttributes is a read-only NamedNodeMap that preserves object identity across all chunks of a single template.

Alternatives Considered

  • New record type ("parsedElement"): 2× record allocations
  • DOM events (parseend / patch): Interrupts parser
  • Separate PatchObserver: Splits parser from dynamic DOM

As discussed in #110, synchronous events pause the parser, and a separate observer loses ordering with ordinary DOM mutations. Enriched MutationRecords deliver microtask-batched metadata in lockstep with DOM changes.
