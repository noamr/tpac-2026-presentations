Client-side reflection of server-driven UI

Explainer: https://github.com/WICG/declarative-partial-updates/blob/main/parser-mutation-records-explainer.md. Overall theme: client-side reflection of server-driven UI—parseEnd is for hydration & subtree readiness, and template is for flow control & error recovery.

1. Hydration (parseEnd): The Problem (dom#662, wc#809)

<!-- Chunk 1 --> <s-select><s-option>A</s-option> <!-- Chunk 2 --> <s-option>B</s-option></s-select>
  • Parser inserts elements on the start tag
  • addedNodes & connectedCallback() run before children exist
  • No signal when </s-select> is ready to hydrate

When the HTML parser sees a start tag, it inserts the element into the DOM immediately before parsing its children. If a network chunk splits inside the element, addedNodes and connectedCallback() see a half-parsed subtree with no signal when the closing tag arrives.

1. Hydration & Subtree Readiness

  • Compound components (wc#809) — <s-select> indexing <s-option>s, tabs, tables, 3D scenes
  • Island hydration — hydrate SSR component only once its full subtree is in the DOM
  • DOM morphing & swapping (dom#1116) — don't diff/delete children that haven't streamed in yet
  • Entry animations & View Transitions (html#12200) — measure & animate complete subtrees

Four structural (non-text) use cases: (1) compound custom elements like <s-select>, tabs, data tables, or WebGL scenes that index/validate child elements and want to avoid O(N^2) work or false "missing child" errors mid-stream; (2) streaming DOM morphers (idiomorph, Turbo, Marko) that otherwise delete existing live DOM nodes because the incoming subtree isn't finished yet; (3) SSR island hydration that expects the component's full DOM tree; and (4) View Transitions and entry animations on complete subtrees ( plus text/code evaluation like syntax highlighters and math blocks).

Parse End: Workarounds Today

  • Wait for DOMContentLoaded — kills streaming UX
  • setTimeout / rAF — races with slow network chunks
  • nextSibling ancestor walks — 100ms+ main-thread cost

Today libraries choose between waiting for DOMContentLoaded (giving up incremental rendering), timers (which break on slow networks), or walking ancestors on every MutationRecord to check for a nextSibling (which costs 100ms+ on large pages and still fails for last-child chains).

2. Flow & Error Control (template): The Problem (#110)

<!-- Target: <main><?start name="results">...<?end></main> --> <template for="results" data-turn="3"> <p>Streamed response...</p> </template>
  • Parser consumes <template for> — never enters the DOM
  • MutationObserver only sees inner nodes land in <main>
  • Server control envelope, metadata, and aborts are lost

When the parser processes a <template for> patch, it consumes the <template> element itself and streams its content directly into the target region (<?start name="results"> inside <main>). MutationObserver only sees individual child insertions inside <main>—the patch wrapper, its attributes, and its start/end/abort boundaries are completely invisible.

2. Patch Flow Control & Error Recovery

  • Flow control: know when a streamed patch starts and finishes
  • Error recovery: detect aborted patches (truncated stream / missing target)
  • Server metadata: read patch attributes (data-turn="3", request IDs)
  • Attribution: separate server patches from client edits

What applications need from <template for> observation (#110 from OpenAI, html#13008): (1) attribution—telling server-streamed patches apart from local client mutations; (2) reading metadata attributes like data-turn="3" off the template; (3) lifecycle hooks for patch start and completion; and (4) error recovery when a stream truncates before </template> or targets a missing marker.

Parsing vs. Imperative & Dynamic DOM

“If we expose a parser-completion hook, developers will rely on it and break imperative DOM creation (createElement + appendChild).”

  • connectedCallback() is sync: body.append(el); el.append(child); runs before child is appended
  • MutationObserver is microtask-batched: sync append(el) + el.append(child) finish before the callback runs (!el.isParsing)
  • Custom elements: start mo.observe(this, { childList: true, parseEnd: true }) in constructor()

Why MutationObserver avoids the classic connectedCallback() / parsedCallback() trap: if someone writes const el = document.createElement('s-select'); document.body.append(el); el.append(option);, connectedCallback() fires synchronously on body.append(el) before option is attached. By contrast, a MutationObserver started in constructor() (or on the document) runs at the microtask checkpoint—after both synchronous append() calls have completed—and sees el with its children and !el.isParsing, right alongside ongoing childList mutations.

Proposal

observer.observe(document, { childList: true, subtree: true, parseEnd: true, template: true });
  • element.isParsing — still open in the parser?
  • parseEnd: true — notify when an open element closes
  • template: true — expose <template for> status & attributes

Two opt-in flags on MutationObserverInit—parseEnd: true and template: true—plus element.isParsing (and record.parserContextElement for fragment parsing).

1. Parse End (parseEnd: true)

for (const r of records) { for (const n of r.addedNodes) if (!n.isParsing) setup(n); // closed in same chunk if (!r.addedNodes.length && !r.removedNodes.length && !r.target.isParsing) setup(r.target); // closed in later chunk }

Because MutationObserver runs in a microtask after the chunk finishes, same-chunk elements already have isParsing === false when seen in addedNodes. Only elements still open across a chunk boundary emit an empty childList record (target === closedElement, previousSibling === el.lastChild) when their end tag arrives.

2. Patching (template: true)

const target = r.templateAttributes?.get("for"); const turn = r.templateAttributes?.get("data-turn"); // r.templateStatus: "start" | "update" | "end" | "abort"
  • templateAttributes — ReadOnlyMap of active <template for> attributes (shared identity per patch)
  • templateStatus — "start" → "update" → "end" | "abort"

Every record produced during a patch carries templateAttributes (a read-only Map shared across all records of that patch so r1.templateAttributes === r2.templateAttributes) and templateStatus ("start", "update", "end", or "abort" if truncated at EOF or missing its target).

Why Not...

  • record.parsedElements list: extra allocation; requires observing parent
  • "parseEnd" record type: 2× records for same-chunk elements
  • DOM events / PatchObserver: pauses parser or loses mutation order

As discussed in #110, synchronous events pause the parser, and a separate observer loses ordering with ordinary DOM mutations. Enriched MutationRecords deliver microtask-batched metadata in lockstep with DOM changes.
