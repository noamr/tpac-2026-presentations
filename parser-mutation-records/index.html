Explainer: https://github.com/WICG/declarative-partial-updates/blob/main/parser-mutation-records-explainer.md. Proposes extending MutationObserver with { parser: true } and Node/ShadowRoot with isParsing.

The Parser–DOM Gap

The HTML parser tracks state that vanishes before reaching the DOM:

  • Open-element stack — is an element still receiving children, or closed (</el>)?
  • Consumed <template>s — shadowrootmode & for never enter the tree
  • Fragment context — which root triggered innerHTML, streamHTML*, or a patch?

As HTML gains more streaming and declarative primitives (Declarative Shadow DOM, <template for>, element.streamHTMLUnsafe), the gap between what the parser is doing and what MutationObserver reports has become a major pain point.

Why It Hurts Today

  • addedNodes fires on start tags — children may arrive in later network chunks
  • nextSibling workarounds cost 100ms+ and fail on last-child elements
  • Declarative Shadow Roots attach silently (zero MutationRecords)
  • Streaming <template for> patches look identical to ordinary DOM mutations

Custom elements and hydration libraries cannot tell if an element's children have finished parsing (whatwg/dom#898, w3c/webcomponents#809). Polyfills and DevTools cannot detect when a declarative shadow root is attached or when a streaming patch starts, updates, or aborts.

Proposal: { parser: true }

observer.observe(document, {
  childList: true,
  subtree: true,
  parser: true
});
  • element.isParsing / shadowRoot.isParsing getter
  • record.parsedElements (NodeList)
  • record.templateStatus & record.templateAttributes
  • record.parserContextElement

All parser metadata is opt-in via parser: true on MutationObserverInit, keeping existing observers 100% backward compatible with zero extra overhead.

isParsing & parsedElements

// Chunk 1: "<my-card><h2>Title</h2>"
//   addedNodes: [my-card], parsedElements: []
//   myCard.isParsing === true

// Chunk 2: "<p>Body</p></my-card>"
//   target: my-card, addedNodes: [p], parsedElements: [p, my-card]
//   myCard.isParsing === false

Coalesced onto existing childList records whenever possible — no extra records.

When an element opens and closes in the same chunk, it appears in both addedNodes and parsedElements of the same MutationRecord. If split across network chunks, parsedElements is attached to the last child record or a standalone record on close.

Observing Consumed <template>s

Tracks <template shadowrootmode> and <template for> / <template src>:

  • templateStatus: "start" → "update" → "end" (or "abort")
  • templateAttributes: read-only NamedNodeMap of the consumed <template>
  • Same templateAttributes object identity across all chunks of one template

Because parser-consumed templates are never inserted into the DOM, exposing their attributes via a read-only NamedNodeMap avoids retaining detached DOM trees while still letting observers read for, src, shadowrootmode, or custom data-* attributes.

Example: DSD & Streaming Patches

for (const r of records) {
  if (r.templateStatus === "start" &&
      r.templateAttributes.getNamedItem("shadowrootmode")) {
    observeShadowRoot(r.target.shadowRoot);
  }
  if (r.templateStatus === "end" &&
      r.templateAttributes.getNamedItem("for")) {
    finalizePatch(r.parserContextElement, r.templateAttributes);
  }
}

A single observer can now discover Declarative Shadow Roots the moment they attach (even if empty) and track the exact start, chunked updates, and completion of streaming HTML patches.

parserContextElement

  • Points to the fragment root for innerHTML, setHTML, streamHTML*, or <template for>
  • null for the main document parser or imperative DOM calls (appendChild)
  • Lets a single document-wide observer attribute mutations to the container being updated

When a subtree observer sits on document.body, mutations deep inside a patched container have r.target set to the immediate parent. parserContextElement tells the observer which container initiated the fragment parse.

Alternatives Considered

  • New MutationRecord.type ("parsedElement") — doubles record allocations during initial page parse
  • DOM events (parseend, patchstart) — repeats MutationEvent per-node dispatch overhead
  • Separate PatchObserver — splits ordering between DOM insertions and parser boundaries

Piggybacking on MutationObserver's existing microtask batching and coalescing parsedElements onto childList records keeps memory and CPU overhead near zero.

Open Questions & Discussion

  • Custom Element ergonomics: add parsedCallback() & shadowRootAttachedCallback()?
  • Should DSD "start" include [shadowRoot] in addedNodes?
  • Feedback on { parser: true } shape and attribute map ergonomics

If we add parsedCallback() on Custom Elements, its semantics can be defined directly on top of isParsing (firing once per connection after isParsing becomes false), while MutationObserver handles general subtree observation.
