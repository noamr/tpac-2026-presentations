30 Years of Trying

  • 1995–2001: SSI, PHP, ESI — server-only
  • 2008–2016: <iframe seamless> — not really an include
  • 2013–2018: <link rel="import"> — gone
  • 2017–Today: whatwg/html#2791 — 280+ comments, 225+ 👍

Including one piece of HTML inside another is one of the oldest requests on the web. SSI and PHP were invented for it in 1995. On the client, <iframe seamless> had heavy Window/Document overhead and style/security issues, and HTML Imports loaded an inert document that still needed JS to stamp DOM. Meanwhile whatwg/html#2791 has been active since 2017.

Developers Still Want This

“PHP was literally created to solve this problem… Imagine if the client could cache the entire header and footer and only need to download the main content.”

— @grepsedawk (whatwg/html#2791)

“DRY HTML authoring without running code server-side or requiring JS. It's actually what I naively expected HTML imports to do at first.”

— @brandondees (74 👍) · GitHub has used <include-fragment> in prod for 10+ years (@josh)

Developers in whatwg/html#2791 repeatedly highlight both the beginner/static-site ergonomics and the caching win of client-side includes. GitHub has used its <include-fragment> custom element in production for over a decade as a client-evaluated <esi:include>.

Why It Stalled

  1. Parser-blocking waterfalls
  2. FOUC & layout shifts
  3. XSS

Client-side includes stalled on three core problems: synchronous fetching created parser-blocking network waterfalls, asynchronous fetching caused FOUC and layout shifts, and injecting fetched HTML carried XSS risk without a native sanitizer.

What Changed?

  1. Out-of-Order Streaming (<template for>)
  2. Render-Blocking (rel="expect") & a new proposed buffer attribute
  3. Sanitizer API

Each of those three blockers now has a platform primitive: out-of-order streaming (<template for>) decouples fetching from parser position, rel="expect" and buffer prevent FOUC and manage layout shifts, and the Sanitizer API makes external markup safe by default.

Proposal: <template src>

<!-- Targeted include --> <main><?start name="feed">Loading...<?end></main> <template for="feed" src="feed.html"></template> <!-- In-place include --> <template for src="header.html"></template>
  • for="name": Fetches a <template> to replace a matching PI
  • Empty for: Fetches and replaces the <template> in place
  • No for: An ordinary <template>

An empty for attribute replaces the <template> itself in place and removes the template when done; for="name" streams into a named target range; and src without for fetches an inert <template> for later cloning.

1. Parser Order ≠ Document Order

<main> <?start name="feed"><p class="skeleton">Loading...</p><?end> </main> <footer>...</footer> <template for="feed" src="feed.html"></template>
  • Decouples fetch from DOM position
  • Streams into the target slot as bytes arrive

First mitigation: instead of blocking the HTML parser on a synchronous fetch, <template src> fetches asynchronously and combines with <template for> so fetches can start early in the document while the parser renders placeholders and the rest of the page in parallel.

2a. Render-blocking instead of parser-blocking

<head> <link rel="expect" href="#content" blocking="render"> </head> <body> <template for src="header.html"></template> <main id="content">Content</main> </body>
  • Expecting an element blocks on any client-side include before it
  • <main> parses in parallel; paints together with header.html

Second mitigation (part 1): if element render-blocking (<link rel="expect" href="#content" blocking="render">) expects an element, it also waits for any client-side includes preceding that element in tree order (while ignoring includes after it). The HTML parser continues through <main> without blocking, and header + main paint together.

2b. Buffered Includes (buffer)

<!-- Default: streams into DOM --> <template for="feed" src="feed.html"></template> <!-- Buffered: atomic swap on EOF --> <template for="feed" src="feed.html" buffer></template>
  • Parses off-screen; swaps placeholder atomically on EOF
  • External resources inside the fragment are fetched speculatively

Second mitigation (part 2): for async fragments that shouldn't block initial page render, adding buffer parses the response off-screen into template.content while speculatively fetching its external resources, then swaps the placeholder atomically on EOF.

buffer on the Main Stream

<template for buffer> <link rel="stylesheet" href="widget.css"> <img src="avatar.jpg"> <div class="widget">...</div> </template> <template for="comments" buffer>...</template>
  • Works on inline sections and patches too (no src needed)
  • External resources are fetched speculatively

Because buffer is a general <template> primitive rather than a fetch-only flag, you can also use <template for buffer> on the incoming main HTML stream. External resources inside the buffered template are fetched speculatively by the preload scanner while buffering.

3a. Safe by Default (sanitize)

<button class="icon-btn"> <template for src="https://icons.example/star.svg" crossorigin></template> Star </button> <template for src="trusted-app.html" sanitize="unsafe"></template>
  • src is sanitized by default (sanitize="unsafe" opts out)
  • 3P inline SVG: Stylable with CSS (currentColor), sanitized, off the main stream

Third mitigation (part 1): external includes (<template src>) are sanitized by default using the browser's built-in Sanitizer API. A great example is including a third-party SVG as an inline <svg> in the DOM—stylable with CSS currentColor, cached separately off the main stream, and safely sanitized without XSS risk.

sanitize on the Main Stream

<template for sanitize> <article class="user-comment"> Hello! <script> evil() </script> </article> </template> <template for="comments" sanitize>...</template>
  • Declarative sanitization for inline markup & SSR patches

Just like buffer, sanitize works without src too. While inline <template for> is unsanitized by default because it's part of the main document stream, adding sanitize lets server-rendered pages declaratively sanitize untrusted regions or streamed patches directly in the HTML parser.

3b. Defense in Depth with CSP

Content-Security-Policy: fragment-src 'self' https://cdn.example; script-src 'self' 'nonce-r4nd0m'
  • fragment-src: Allowed fragment origins (falls back to default-src)
  • script-src: Still governs scripts inside sanitize="unsafe"

Third mitigation (part 2): CSP provides defense in depth. A new fragment-src directive (falling back to default-src) restricts where fragments can be fetched from, and even when sanitize="unsafe" is set, any scripts inside the fragment remain governed by the document's script-src policy.

Why <template>?

  • Why not <fragment>? <template> already disappears from the DOM (shadowrootmode, for)
  • Valid everywhere in the parser (<table>, <select>)
  • Why not <script type="html">? No inline HTML

A new <fragment> element is rejected because <template> already has the self-consuming "disappear from the DOM" behavior and is valid everywhere in the HTML parser without foster-parenting.
