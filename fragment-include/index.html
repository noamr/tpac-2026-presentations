30 Years of Trying

  • 1995–2001: SSI, PHP, ESI — server-only
  • 2008–2016: <iframe seamless> — not really an include
  • 2013–2018: <link rel="import"> — gone
  • 2017–Today: whatwg/html#2791 — 280+ comments, 225+ 👍

Including one piece of HTML inside another is one of the oldest requests on the web. SSI and PHP were invented for it in 1995. On the client, <iframe seamless> had heavy Window/Document overhead and style/security issues, and HTML Imports loaded an inert document that still needed JS to stamp DOM. Meanwhile whatwg/html#2791 has been active since 2017.

Developers Still Want This

“PHP was literally created to solve this problem… Imagine if the client could cache the entire header and footer and only need to download the main content.”

— @grepsedawk (whatwg/html#2791)

“DRY HTML authoring without running code server-side or requiring JS. It's actually what I naively expected HTML imports to do at first.”

— @brandondees (74 👍) · GitHub has used <include-fragment> in prod for 10+ years (@josh)

Developers in whatwg/html#2791 repeatedly highlight both the beginner/static-site ergonomics and the caching win of client-side includes. GitHub has used its <include-fragment> custom element in production for over a decade as a client-evaluated <esi:include>.

Why It Stalled

  1. Parser-blocking waterfalls: Sync fetching halts the parser
  2. FOUC & layout shifts: Async fragments paint unstyled or push content around
  3. XSS: Injecting raw HTML without a built-in sanitizer

Client-side includes stalled on three core problems: synchronous fetching created parser-blocking network waterfalls, asynchronous fetching caused FOUC and layout shifts, and injecting fetched HTML carried XSS risk without a native sanitizer.

What Changed?

  1. Out-of-Order Streaming (<template for>) — fetch in parallel without blocking the parser
  2. Render-Blocking (rel="expect") & buffer — control when fragments paint
  3. Sanitizer API — safe by default in the parser

Each of those three blockers now has a platform primitive: out-of-order streaming (<template for>) decouples fetching from parser position, rel="expect" and buffer prevent FOUC and manage layout shifts, and the Sanitizer API makes external markup safe by default.

Proposal: <template src>

<!-- In-place include --> <template for src="header.html"></template> <!-- Targeted include --> <main><?start name="feed">Loading...<?end></main> <template for="feed" src="feed.html"></template>
  • Self-removes when done — zero DOM footprint

A <template> becomes active when it has for, src, or both. For in-place includes, it acts as a temporary insertion anchor and removes itself on completion. Disconnecting it mid-fetch aborts the network request.

1. Breaking the Waterfall

<!-- Kick off fetch early in <head> or body without blocking parser --> <template for="feed" src="feed.html"></template> <!-- Parser continues; slot updates when data arrives --> <main> <?start name="feed"><p class="skeleton">Loading...</p><?end> </main>
  • Decoupled fetch & placement: Start fetching early; main document keeps parsing
  • Streams by default: Content flows straight into the target range as bytes arrive

First mitigation: instead of blocking the HTML parser on a synchronous fetch, <template src> fetches asynchronously and combines with <template for> so fetches can start early in the document while the parser renders placeholders and the rest of the page in parallel.

Render-blocking instead of parser-blocking

<head> <link rel="expect" href="#site-header" blocking="render"> </head> <body> <!-- header.html contains <header id="site-header">...</header> --> <template for src="header.html"></template> <main>Content</main> </body>
  • Element render-blocking waits for client-side includes: Main document EOF doesn't prematurely unblock rel="expect" while <template for src> fetches are in flight
  • Parser keeps going: <main> parses in parallel and paints together with #site-header

Second mitigation (part 1): placing <link rel="expect" href="#site-header" blocking="render"> in <head> holds initial paint while pending <template for src> fetches are in flight, unblocking as soon as #site-header is parsed so above-the-fold chrome doesn't push <main> down.

2b. Buffered Includes (buffer)

<!-- Default: streams straight into DOM as bytes arrive --> <template for="feed" src="feed.html"></template> <!-- Buffered: parses off-screen & swaps atomically on EOF --> <template for="feed" src="feed.html" buffer></template>
  • No half-rendered states: Placeholder stays intact until the full fragment is ready
  • No FOUC: Waits for <link rel="preload"> styles inside the fragment before committing

Second mitigation (part 2): for async fragments that shouldn't block initial page render, adding buffer parses the response off-screen into template.content, waits for any preloaded stylesheets inside the fragment, and swaps the placeholder atomically on EOF.

3a. Safe by Default (sanitize)

<!-- Default: sanitized via built-in Sanitizer API --> <template for src="widget.html"></template> <!-- Explicit opt-out when scripts are needed --> <template for src="trusted-app.html" sanitize="unsafe"></template>
  • Sanitized by default: Strips <script>, inline event handlers, and dangerous URLs
  • Inline <template for> (no src): Unsanitized (already part of the main document stream)

Third mitigation (part 1): external includes (<template src>) are sanitized by default using the browser's built-in Sanitizer API. Authors must explicitly write sanitize="unsafe" to allow scripts inside an external fragment.

3b. Defense in Depth with CSP

Content-Security-Policy: fragment-src 'self' https://cdn.example; script-src 'self' 'nonce-r4nd0m'
  • fragment-src: Restricts which origins <template src> can fetch from (falls back to default-src)
  • script-src still applies: Even with sanitize="unsafe", scripts inside fragments must pass the document's script-src policy

Third mitigation (part 2): CSP provides defense in depth. A new fragment-src directive (falling back to default-src) restricts where fragments can be fetched from, and even when sanitize="unsafe" is set, any scripts inside the fragment remain governed by the document's script-src policy.

Why <template>?

  • Why not <fragment>? <template> already has the “disappear from the DOM” behavior (shadowrootmode, for)
  • Works everywhere in the parser — including inside <table> & <select>
  • Why not <script type="html">? Wrong defaults, no inline HTML

A new <fragment> element is rejected because <template> already has the self-consuming "disappear from the DOM" behavior and is valid everywhere in the HTML parser without foster-parenting.
