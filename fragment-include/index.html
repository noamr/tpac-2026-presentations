30 Years of Trying to Include HTML

  • 1995–2001: Server-Side Includes (<!--#include -->), PHP, Edge-Side Includes (<esi:include>)
  • 2008–2016: <iframe seamless> — removed (heavy Window/Document, style & security issues)
  • 2013–2018: HTML Imports (<link rel="import">) — removed (inert doc, required JS to stamp DOM)
  • 2017–Today: whatwg/html#2791 — 280+ comments, 225+ 👍, custom elements (<include-fragment>)

Including one piece of HTML inside another is one of the oldest requests on the web. SSI and PHP were literally invented for it in 1995. On the client, <iframe seamless> and HTML Imports both tried and failed, while whatwg/html#2791 has been active since 2017 with hundreds of comments and thumbs-ups.

What Developers Have Been Saying

“Re-using blobs of HTML is needed in pretty much every multi-page website. However, to do that today, you need either JS, or build tools… Not everyone was using the same date picker, but almost everyone needed a date picker. I'd argue this falls into that category.”

— Lea Verou (whatwg/html#2791)

“A way for DRY HTML authoring without the burden of running code server-side or requiring JS. It's actually what I naively expected HTML imports to do at first.”

— @brandondees (74 👍 on #2791) · GitHub shipped <include-fragment> in production for 10+ years (@josh)

Developers across the spectrum—from educators and static site authors to large apps like GitHub using <include-fragment>—have repeatedly asked for a native HTML equivalent to CSS @import and JS import.

Why Was It Rejected Until Now?

  • “Just do it on the server or in a build tool” — ignored static sites, client-cached shared chrome, and independent async widgets
  • Sync vs. Async Dilemma:
    • “Synchronous fetching is a big no-no.” (@annevk) — blocks the HTML parser
    • Naive async fetching caused FOUC, half-rendered UI, and layout shifts
  • No Built-in Sanitizer: Injecting external HTML was either an XSS hazard or required JS sanitizers
  • HTML Parser Grammar: A new <include> tag gets foster-parented out of <table> & <select>

Why did #2791 stall for 9 years? First, synchronous fetching blocks the parser, while naive async fetching caused FOUC and layout shifts. Second, there was no native HTML sanitizer in the browser. Third, introducing a new <include> element breaks inside <table>, <tr>, and <select> due to HTML parser foster-parenting rules.

Why Now Is the Time

  1. Native Sanitizer API: Browser-native, parser-integrated sanitization is now built in — <template src> can be safe by default
  2. Out-of-Order Streaming & Rendering Primitives:
    • <template for> + <?start> / <?marker> for declarative targeting
    • buffer mode + preload gating + <link rel="expect" blocking="render"> eliminate FOUC & CLS without sync fetching
  3. <template> Parser Superpowers: Already valid anywhere in HTML (<table>, <select>, <head>, Shadow DOM)

All three missing pieces have now landed in the platform: the Sanitizer API gives us safe-by-default inclusion, out-of-order streaming (<template for>) plus rel="expect" and buffer mode solve async rendering and layout shift, and <template> already bypasses foster-parenting everywhere in the HTML parser.

Complements HTML Patching (<template for>)

  • External Fetching (src): No need to multiplex every auxiliary widget (comments, sidebar, ads) in the main server stream
  • Atomic Buffering (buffer): Avoid chunk-by-chunk layout jank when desired
  • Independent Trust Boundary (sanitize): Sanitize third-party or user fragments separately from the main page

HTML patching (<template for>) handles out-of-order streaming inside a single response, while Fragment Include extends the exact same <template> primitive to external fetches, buffered commits, and independent sanitization.

Proposal: Extend <template>

  • for — target a <?start> / <?marker> slot, or render in-place
  • src — asynchronously fetch an external HTML fragment
  • buffer — parse off-screen, insert atomically when complete
  • sanitize — safe by default for external src, opt-in for inline

A <template> becomes active when it has for, src, or both. Without either, it remains a classic inert template. Standard fetch attributes (nonce, crossorigin, referrerpolicy) are reused; fetches are always non-blocking.

In-Place & Targeted Includes

<!-- In-place include (sanitized by default) -->
<template src="header.html"></template>

<!-- Targeted include with fallback -->
<main>
  <?start name="feed">Loading feed...<?end>
</main>
<template for="feed" src="feed.html"></template>

Once finished, the <template> removes itself — leaving zero DOM footprint.

For in-place includes (src without for, or empty for=""), the browser temporarily attaches the <template> at its declared position as the insertion anchor, inserts nodes before it, and removes the <template> on completion. Disconnecting the template mid-fetch aborts the network request immediately.

Streaming vs. Buffered (buffer)

Streaming (default)

Chunks parse directly into the live DOM as bytes arrive.

<template
  for="rows"
  src="rows.html">
</template>

Buffered (buffer)

Parses into template.content; commits atomically on EOF.

<template
  for="comments"
  src="comments.html"
  buffer>
</template>

Streaming is ideal for long feeds or table rows. Buffering avoids half-rendered UI and layout jank for self-contained widgets, modals, or comment sections.

Subresource Gating in buffer Mode

<!-- widget.html -->
<link rel="preload" href="widget.css" as="style">
<link rel="modulepreload" href="widget.js">

<div class="widget">
  <link rel="stylesheet" href="widget.css">
  <p>Ready without FOUC</p>
</div>

Preloads inside <template buffer> fetch immediately and gate the atomic DOM commit.

Normally <link rel="preload"> inside an inert <template> does nothing. In an active buffered template, preloads and modulepreloads start fetching as soon as they are parsed, and the DocumentFragment only commits to the live DOM once those preloads finish (or fail), preventing FOUC without blocking the main parser.

Avoiding Layout Shifts

<head>
  <link rel="expect" href="#site-header" blocking="render">
</head>
<body>
  <template src="header.html"></template>
  <main>Main content painted together with #site-header</main>
</body>
  • rel="expect" stays render-blocking while pending <template src> includes may still provide #site-header

If the main document reaches EOF and #site-header hasn't appeared yet, render-blocking stays active while any <template src> fetches are in flight, unblocking as soon as #site-header finishes parsing. We also explore <link rel="expect" href="header.html" blocking="render"> or <template for="..." src="..." blocking="render"> in <head>.

Security & Sanitization

Mode Default Override
External (src="...") Sanitized (scripts stripped) sanitize="unsafe"
Inline (no src) Unsafe (matches patching) sanitize

CSP: New fragment-src directive + standard script-src enforcement.

External includes are safe by default via the Sanitizer API. Opting out requires sanitize="unsafe", and even then CSP fragment-src controls allowed origins while script-src (nonces/hashes) still governs any scripts inside the fragment.

Alternatives Considered

  • <script type="html" src="..."> — parser-blocking legacy defaults; can't hold inline HTML
  • New <fragment> element — foster-parented out of <table>, <select>, etc.
  • Global buffer / sanitize attributes — permanent DOM clutter & false security promises for innerHTML

<template> is uniquely privileged in the HTML parser: it is valid anywhere in the grammar (including inside tables and selects) and already acts as a self-consuming parser directive for shadowrootmode and for.
