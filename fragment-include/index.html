30 Years of Trying

  • 1995–2001: SSI, PHP, ESI — server-only
  • 2008–2016: <iframe seamless> — not really an include
  • 2013–2018: <link rel="import"> — gone
  • 2017–Today: whatwg/html#2791 — 280+ comments, 225+ 👍

Including one piece of HTML inside another is one of the oldest requests on the web. SSI and PHP were invented for it in 1995. On the client, <iframe seamless> had heavy Window/Document overhead and style/security issues, and HTML Imports loaded an inert document that still needed JS to stamp DOM. Meanwhile whatwg/html#2791 has been active since 2017.

Developers Still Want This

“PHP was literally created to solve this problem… Imagine if the client could cache the entire header and footer and only need to download the main content.”

— @grepsedawk (whatwg/html#2791)

“DRY HTML authoring without running code server-side or requiring JS. It's actually what I naively expected HTML imports to do at first.”

— @brandondees (74 👍) · GitHub has used <include-fragment> in prod for 10+ years (@josh)

Developers in whatwg/html#2791 repeatedly highlight both the beginner/static-site ergonomics and the caching win of client-side includes. GitHub has used its <include-fragment> custom element in production for over a decade as a client-evaluated <esi:include>.

Why It Stalled

  • “Just do it on the server”
  • Sync fetch: “A big no-no” (@annevk)
  • Async fetch: FOUC & layout shifts
  • Security: XSS without a native sanitizer

Why was it rejected for so long? First, "do it on the server" ignored static sites, client-cached chrome, and independent async widgets. Second, synchronous fetching blocks the parser, while naive async fetching caused FOUC and layout shifts. Third, there was no built-in HTML sanitizer.

What Changed?

We finally have the building blocks to do this safely:

  1. Sanitizer API — safe by default
  2. Render-Blocking (rel="expect") & buffer — manage layout shifts & FOUC
  3. Out-of-Order Streaming (<template for>) — declarative slots

For years, fear of footguns (FOUC, layout shifts, XSS) kept client-side includes out of the platform, pushing developers into heavy JS or server-only setups. Now we have the Sanitizer API, rel="expect" to balance speed and smoothness, and <template for>—so we can make the simple thing safe.

Proposal: Extend <template>

<!-- In-place include --> <template src="header.html"></template> <!-- Targeted include --> <main><?start name="feed">Loading...<?end></main> <template for="feed" src="feed.html"></template>
  • Self-removes when done — zero DOM footprint

A <template> becomes active when it has for, src, or both. For in-place includes, it acts as a temporary insertion anchor and removes itself on completion. Disconnecting it mid-fetch aborts the network request.

Streaming vs. buffer

Streaming (default)

<template for="rows" src="rows.html"> </template>

Streams straight into DOM.

Buffered (buffer)

<template for="comments" src="comments.html" buffer> </template>

Commits atomically on EOF.

Streaming is default. Adding buffer parses off-screen into template.content and inserts atomically on EOF. Preloads (<link rel="preload">, modulepreload) inside a buffered template fetch immediately and gate the atomic commit so styles are ready without FOUC.

Managing Layout Shifts

<link rel="expect" href="#site-header" blocking="render"> <template src="header.html"></template> <template for="feed" src="feed.html" buffer></template>

If the main document reaches EOF before #site-header is parsed, render-blocking stays active while pending <template src> fetches are in flight, unblocking as soon as #site-header finishes parsing.

Security

  • <template src>: Sanitized by default
  • Opt-out: sanitize="unsafe"
  • CSP: fragment-src + script-src

External includes are sanitized by default using the browser's native Sanitizer API. Opting out requires sanitize="unsafe" and is still governed by CSP fragment-src and script-src.

Why <template>?

  • Why not <fragment>? <template> already has the “disappear from the DOM” behavior (shadowrootmode, for)
  • Works everywhere in the parser — including inside <table> & <select>
  • Why not <script type="html">? Wrong defaults, no inline HTML

A new <fragment> element is rejected because <template> already has the self-consuming "disappear from the DOM" behavior and is valid everywhere in the HTML parser without foster-parenting.
