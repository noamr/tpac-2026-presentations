Recap: Connection Allowlists

Connection-Allowlist: (response-origin "https://*.site.example" "https://cdn.example"); redirects=block; webrtc=block; report-to=endpoint
  • Block outbound connections outside the allowlist
  • Fetch, navigations, WebSockets, WebTransport, WebRTC, preconnect
  • Graduated to W3C WebAppSec WG

Connection Allowlists focuses purely on exfiltration defense-in-depth: a single Structured Field header using URLPattern syntax that blocks unauthorized connections across Fetch, navigations, WebRTC, WebTransport, Workers, Early Hints, and preconnect/dns-prefetch. Graduation to W3C WebAppSec WG is approved.

Special Cases: Redirects & WebRTC

  • Redirects (#7): Pattern-matching redirect targets leaks cross-site URLs → governed by redirects=allow|block (default block)
  • WebRTC: Peer candidates use raw IPs (not URLs) → governed by webrtc=allow|block (default block)

Two protocol special cases: (1) Redirects (#7): matching redirect targets against URLPatterns would leak cross-origin redirect destinations via blocking or reporting, so redirects are controlled by a coarse redirects=allow|block parameter (default block). (2) WebRTC: peer-to-peer ICE candidates only have raw IP:port addresses rather than URLs, so WebRTC is controlled by a coarse webrtc=allow|block parameter (default block).

User Agency (#31)

  • Rule of thumb: if page JS could preventDefault() it, we can block it
  • If it's browser chrome (address bar, extensions, context menus), hands off
  • Tension: User gesture + page-crafted URL

In #31, concerns were raised around RFC 8890 (The Internet is for End Users) and user agency. Our guiding principle is that Connection Allowlists only restrict actions the website could already initiate or block on its own (like fetch() or in-page clicks where JS can call preventDefault()). Explicit browser gestures—like context-menu "Open Link in New Tab" or extensions—remain under user control. That boundary leads directly into our open issues.

Open Issues: Navigation & Gestures

  • #5 Context menus: Browser gesture, but page can swap href on right-click
  • #40 Custom schemes (mailto:, intent:): Non-HTTP, but passes page payload to external apps
  • #27 client.navigate(): Enforce SW allowlist, document allowlist, or both?

Each of these sits on the boundary of page-initiated navigation: (#5) "Open Link in New Tab" is a browser context-menu gesture, so we don't block it—but an untrusted href or oncontextmenu handler can still encode sensitive data in the URL. (#40) Custom schemes like mailto: or intent: don't go through HTTP Fetch, yet hand a page-chosen URL out of the browser. (#27) Service Worker client.navigate() crosses two environments, and HTML's navigate algorithm defaults to "browser UI" (no policy container) unless callers pass one.

Open Issues: Sandboxing & Same-Origin

  • #37 Local-scheme iframes (srcdoc, about:blank): Applying policy to dynamically created content
  • #15 response-origin escape: Same-origin fetch needed, but window.open('/404').fetch(...) bypasses policy
  • #7 Redirect default: Keep redirects=block as default, or flip to allow?

Second group of contentions: (#37) Developers isolating AI-generated code ask how to apply a connection allowlist to dynamically created originless iframes before setting their contents. The issue's reply says support is in development; it does not establish an initial-fetch race. The spec snapshots the iframe requirement at navigation time, so attribute changes apply on the next navigation, not retroactively to the current document. (#15) Allowing response-origin lets a sandboxed page open or frame an unprotected same-origin URL (like a default 404 page) and script it to exfiltrate data. (#7) Whether redirection-allowed should be opt-in (default block) or opt-out.

Embedded Enforcement: Why?

  • Gap: A parent's allowlist does not constrain a navigated child frame's connections
  • Risk: A permissive child can exfiltrate data the parent cannot
  • Goal: Let the parent require an outbound allowlist for its child frames
  • Inheritance: Descendant frames may tighten the requirement, never loosen it

frame-src gates what loads, not where the child connects. (#28)

A document's Connection-Allowlist only governs its own connections. Every navigated iframe—both same-origin and cross-origin—gets its own policy container from its own HTTP response headers. Data the parent can't exfiltrate directly could be handed to a permissive child frame. CSP frame-src gates the frame's URL, not its subsequent outbound connections; sandbox restricts capabilities rather than providing a destination allowlist. Embedded enforcement lets the embedder extend its guarantee across the embedded subtree, including third-party content it did not author. Nested frames may tighten an inherited requirement, never loosen it.

Embedded Enforcement: Request

Parent: Require a policy on the child frame.

<iframe src="https://widget.example/" connectionallowlist='("https://api.example" response-origin)'> </iframe>

Browser: Forward it on the frame's navigation request.

Sec-Required-Connection-Allowlist: ("https://api.example" response-origin)

Rechecked on every frame navigation, including self-navigation. Attribute changes apply on the next navigation.

The parent at https://embedder.example sets connectionallowlist on the iframe. The browser forwards its requirement using Sec-Required-Connection-Allowlist so the child server can answer knowingly; this is a browser-generated request header, not one set by page JavaScript. The response is checked before the new child document commits. This mirrors CSP Embedded Enforcement: iframe csp maps to connectionallowlist, Sec-Required-CSP to Sec-Required-Connection-Allowlist, Allow-CSP-From to Allow-Connection-Allowlist-From, and a satisfying Content-Security-Policy to a satisfying Connection-Allowlist. Reuse that mental model and navigation plumbing, not CSP's complex semantic policy comparison.

The navigation-time handshake applies to subframes, not main-frame or same-document navigations. The browser snapshots the requirement on each navigation, including navigations initiated by the child itself, so self-navigation does not escape it. Changing the attribute affects the next navigation, not the already-loaded document. Local-scheme documents such as about:srcdoc and data: instead inherit the requirement without a server handshake. The dynamic-originless-frame use case in issue #37 should be discussed in terms of these lifecycle rules, not an established race.

Embedded Enforcement: Response

A. Child consents: Browser applies the parent's requirement.

Allow-Connection-Allowlist-From: https://embedder.example

Or B. Child supplies its own enforced policy: A subset of the required patterns.

Connection-Allowlist: (response-origin)

Neither? Block the network frame.

Local documents (srcdoc / data:) inherit without an HTTP opt-in.

These are alternative child response headers, not two required headers. Path A: Allow-Connection-Allowlist-From is permission to impose the parent's required policy, not an outbound destination allowlist. Its value is either the exact embedder origin or the standalone wildcard *, accepting any embedder. Partial or wildcard origin patterns such as https://*.example are not supported. The required policy is installed on the committed child document.

Path B needs no Allow-Connection-Allowlist-From header: the enforced response policy already meets the requirement shown on the previous slide. The child drops https://api.example and retains only response-origin. Pattern comparison is conservative syntactic set-membership, not semantic URLPattern containment; equality also satisfies the requirement. If the requirement blocks redirects or WebRTC, the child's policy must block them too. Connection-Allowlist: () satisfies every pattern set, but must still meet those redirect and WebRTC conditions. Report-only cannot satisfy a requirement because it does not block violations.

The requirement does not replace or relax the child's own enforced policy: both constraints apply. When the child already asserts a satisfying policy, the browser need not append a redundant enforced entry, but still stores the requirement for descendants. The inherited requirement remains serialized so response-origin re-resolves against each frame's own response URL; it does not freeze to the parent's origin.

The supplied implementation examples place the check in the browser process before response commit. The blocking statement assumes a valid requirement: malformed iframe requirements are ignored, with any inherited ancestor requirement retained. A malformed child response policy does not count as consent. Without consent or a satisfying enforced policy, a network document subject to a valid requirement fails closed. Local-scheme documents inherit without an HTTP opt-in. The examples describe Chromium's ERR_BLOCKED_BY_RESPONSE error page and intentionally preserve the iframe's layout, matching CSP EE. That error code is an implementation detail, not a cross-browser API guarantee.

Upstreaming to Standards

  • Fetch (#32): Check in Main Fetch + pass environment to obtain a connection
  • HTML (#36): Policy container, <iframe connectionallowlist>, preconnect
  • WebRTC & SW: ICE candidate filtering, navigate(), openWindow()

With graduation to WebAppSec WG approved, our next step is upstreaming the monkey-patches into Fetch, HTML, WebRTC, and Service Workers. In particular, Fetch's low-level "resolve an origin" and "obtain a connection" algorithms need an environment parameter so lower-level connections like WebTransport, preconnect, and dns-prefetch are centrally checked.
