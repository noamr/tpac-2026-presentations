Recap: Connection Allowlists

Connection-Allowlist: (response-origin "https://*.site.example" "https://cdn.example"); report-to=endpoint
  • One job: Block outbound connections not matching the allowlist
  • Covers Fetch, navigations, WebSockets, WebTransport, WebRTC, dns-prefetch, preconnect
  • Graduated to W3C WebAppSec WG

Connection Allowlists focuses purely on exfiltration defense-in-depth: a single Structured Field header using URLPattern syntax that blocks unauthorized connections across Fetch, navigations, WebRTC, WebTransport, Workers, Early Hints, and preconnect/dns-prefetch. Graduation to W3C WebAppSec WG is approved.

User Agency & the Browser Boundary (#31)

  • Core rule: Only block what the page itself can initiate or preventDefault()
  • Browser UI wins: Address bar, bookmarks, extensions, and context menus are not blocked
  • The tension: What when a user gesture uses a page-crafted URL?

In #31, concerns were raised around RFC 8890 (The Internet is for End Users) and user agency. Our guiding principle is that Connection Allowlists only restrict actions the website could already initiate or block on its own (like fetch() or in-page clicks where JS can call preventDefault()). Explicit browser gestures—like context-menu "Open Link in New Tab" or extensions—remain under user control. That boundary leads directly into our open issues.

Open Issues: Navigation & Gestures

  • #5 Context menus (“Open in New Tab”):
    User gesture (out of scope) vs. exfiltration via LLM-generated or oncontextmenu-mutated href
  • #40 Custom schemes (mailto:, intent:, slack:):
    Not a network fetch vs. exfiltrates page data to external apps via URL
  • #27 client.navigate() in Service Workers:
    Enforce the SW's allowlist, the target document's, or both?

Each of these sits on the boundary of page-initiated navigation: (#5) "Open Link in New Tab" is a browser context-menu gesture, so we don't block it—but an untrusted href or oncontextmenu handler can still encode sensitive data in the URL. (#40) Custom schemes like mailto: or intent: don't go through HTTP Fetch, yet hand a page-chosen URL out of the browser. (#27) Service Worker client.navigate() crosses two environments, and HTML's navigate algorithm defaults to "browser UI" (no policy container) unless callers pass one.

Open Issues: Sandboxing & Redirects

  • #37 Dynamic originless iframes (about:blank / srcdoc):
    AI sandboxes want dynamic policies vs. mutating after creation races with active fetches
  • #15 response-origin same-origin escape:
    Needed for same-origin fetches vs. opening an unprotected same-origin page (/404) + eval()
  • #7 Server-side redirects:
    Matching redirect targets leaks cross-origin URLs in reports vs. coarse redirection-allowed flag

Second group of contentions: (#37) Developers isolating AI-generated code in srcdoc/about:blank iframes want to apply connectionAllowlist dynamically without racing initial document creation. (#15) Allowing response-origin lets a sandboxed page open or frame an unprotected same-origin URL (like a default 404 page) and script it to exfiltrate data. (#7) Checking redirect targets against URLPatterns leaks cross-site redirect destinations via reports/blocking, whereas a boolean redirection-allowed flag avoids cross-site leaks but needs a default (allow vs. block).

Why Embedded Enforcement? (#28)

  • Connection-Allowlist only governs a document's own connections
  • Every navigated <iframe> (even same-origin!) brings its own policy container
  • Data passed to a permissive child frame can still be exfiltrated

A document's Connection-Allowlist only governs its own connections. Every navigated iframe—both same-origin and cross-origin—gets its own policy container from its own HTTP response headers. Data the parent can't exfiltrate directly could be handed to a permissive child frame. Embedded enforcement lets the embedder extend its guarantee across the entire embedded subtree.

Embedded Enforcement (<iframe connectionallowlist>)

<iframe connectionallowlist='("https://api.example" response-origin)' src="https://widget.example/"></iframe>
  • Request: Sec-Required-Connection-Allowlist
  • Opt-in: Subset Connection-Allowlist, Allow-Connection-Allowlist-From, or local scheme
  • Inherited: Applies to nested frames & workers

Modeled on CSP Embedded Enforcement: the embedder sets connectionallowlist on the iframe, the browser sends Sec-Required-Connection-Allowlist, and the child must opt in either by serving a subset Connection-Allowlist or returning Allow-Connection-Allowlist-From. The requirement is inherited down the frame tree.

Upstreaming to Standards

  • Fetch (#32): Main Fetch + pass environment into resolve an origin / obtain a connection
  • HTML (#36): Policy container, <iframe connectionallowlist>, dns-prefetch, preconnect
  • WebRTC & Service Workers: ICE candidates + navigate() / openWindow()

With graduation to WebAppSec WG approved, our next step is upstreaming the monkey-patches into Fetch, HTML, WebRTC, and Service Workers. In particular, Fetch's low-level "resolve an origin" and "obtain a connection" algorithms need an environment parameter so lower-level connections like WebTransport, preconnect, and dns-prefetch are centrally checked.
