Recap: Connection Allowlists

Connection-Allowlist: (response-origin "https://*.site.example" "https://cdn.example"); report-to=endpoint
  • One job: Block outbound connections not matching the allowlist
  • Covers Fetch, navigations, WebSockets, WebTransport, WebRTC, dns-prefetch, preconnect
  • Graduated to W3C WebAppSec WG

Connection Allowlists focuses purely on exfiltration defense-in-depth: a single Structured Field header using URLPattern syntax that blocks unauthorized connections across Fetch, navigations, WebRTC, WebTransport, Workers, Early Hints, and preconnect/dns-prefetch. Graduation to W3C WebAppSec WG is approved.

Why Embedded Enforcement?

  • Connection-Allowlist only governs a document's own connections
  • Cross-origin <iframe>s bring their own policy container
  • Data passed to a permissive child frame can still be exfiltrated

A document's Connection-Allowlist only governs its own connections. Because a cross-origin iframe gets its own policy container from its own response, data the parent can't exfiltrate directly could be handed to a permissive child frame. Embedded enforcement lets the embedder extend its guarantee across the entire embedded subtree.

Embedded Enforcement (<iframe connectionallowlist>)

<iframe connectionallowlist='("https://api.example" response-origin)' src="https://widget.example/"></iframe>
  • Request: Sec-Required-Connection-Allowlist
  • Opt-in: Subset Connection-Allowlist, Allow-Connection-Allowlist-From, or local scheme
  • Inherited: Applies to nested frames & workers

Modeled on CSP Embedded Enforcement: the embedder sets connectionallowlist on the iframe, the browser sends Sec-Required-Connection-Allowlist, and the child must opt in either by serving a subset Connection-Allowlist or returning Allow-Connection-Allowlist-From. The requirement is inherited down the frame tree.

Open Issues: Navigation Boundaries

  • #40 Custom schemes: Should mailto:, intent:, slack: navigations be checked?
  • #5 Context menus: Is “Open Link in New Tab” browser-initiated or subject to the allowlist?
  • #27 client.navigate(): Enforce the Service Worker's allowlist, the document's, or both?

First group of open issues—where does page-initiated navigation end? (#40) Navigating to custom schemes like mailto:, intent:, or slack: can exfiltrate data via the URL. (#5) On LLM-generated pages, an anchor's href (or an oncontextmenu mutation) can exfiltrate data when a user clicks "Open Link in New Tab". (#27) HTML's navigate algorithm defaults to no policy container unless passed explicitly, and Service Worker client.navigate() has both a worker and a target document.

Open Issues: Sandboxing & Redirects

  • #37 Dynamic originless iframes: Updating connectionAllowlist on about:blank / srcdoc (AI sandboxes)
  • #15 response-origin escape: Same-origin navigation/window.open to an unprotected page (e.g. /404)
  • #7 Redirects: Default allow vs. block without leaking cross-site redirect targets in reports

Second group of open issues: (#37) Sites isolating AI-generated HTML/JS in originless srcdoc/about:blank iframes want to set or tighten connectionAllowlist dynamically. (#15) Allowing response-origin lets a frame open an unprotected same-origin page like /404 and script it unless navigations or inheritance are constrained. (#7) How should server-side redirects be handled without leaking cross-origin redirect targets to parent reporting endpoints?

Upstreaming to Standards

  • Fetch (#32): Main Fetch + pass environment into resolve an origin / obtain a connection
  • HTML (#36): Policy container, <iframe connectionallowlist>, dns-prefetch, preconnect
  • WebRTC & Service Workers: ICE candidates + navigate() / openWindow()

With graduation to WebAppSec WG approved, our next step is upstreaming the monkey-patches into Fetch, HTML, WebRTC, and Service Workers. In particular, Fetch's low-level "resolve an origin" and "obtain a connection" algorithms need an environment parameter so lower-level connections like WebTransport, preconnect, and dns-prefetch are centrally checked.
