Blurry Images vs. Wasted Bandwidth

Wasted Bandwidth

  • 3x bitmaps on tiny thumbnails
  • 10× over-fetch on object-fit: contain

Blurry Images

  • 33–78% under-fetch on object-fit: cover
  • scale-down & none upscale small images
  • Soft zoomable heroes

Every responsive image trades off sharpness against bandwidth. Today users regularly get the worst of both worlds: wasted megabytes on secondary thumbnails and letterboxed banners, and blurry images on square object-fit: cover cards, upscaled scale-down icons, and zoomable hero photos.

Who Should Hold the Knobs?

  • Browsers: Built for interoperability
  • Websites: Know UX & business trade-offs (hero vs. 40th thumbnail)
  • Missing knobs → lying in srcset (img?w=720 800w)

In 2014 the spec left source selection "implementation-defined" so UAs could guess bandwidth heuristics. Over a decade we learned UAs are built for interop—they can't know if an image is a conversion-critical product photo or a secondary thumbnail. And when a direct knob is missing, developers bend existing attributes backwards (like lying in w descriptors), creating subtle footguns.

1. Standardize Selection (#13077)

  1. targetDensity = devicePixelRatio (UA MAY adjust for user prefs / privacy)
  2. Sort candidates by density ascending (first in document order wins ties)
  3. Select first candidate >= targetDensity, or last (largest) if none
  4. UA MAY reuse an already-loaded candidate with density > selected

Since late 2024, WebKit, Gecko, and Blink all use the same selection algorithm: sort ascending, pick the first candidate >= targetDensity, or the largest if none. We can spec this normatively, with explicit MAY allowances for user preference/privacy DPR adjustments and Chrome's cache reuse of already-loaded higher-res candidates.

2. Target Density Knob (#13069)

<img srcset="150.jpg 150w, 200.jpg 200w, 300.jpg 300w" sizes="auto" densityscale="0.75" loading="lazy">

Replaces lying in w descriptors (img?w=720 800w).

Because lying in sizes breaks sizes="auto", production sites like Airbnb literally lie in their w descriptors (writing 800w for a 720px file), which breaks CDN cache sharing and 2D aspect ratios. A densityscale (or resolutionpriority) knob gives sites direct control.

3. object-fit Selection (#12248)

<img sizes="auto" srcset="s.jpg 50w 100h, l.jpg 100w 200h" style="width: 100px; height: 100px; object-fit: contain | cover">

In a 100×100 container with 50×100 and 100×200 sources, the right source depends on object-fit: contain renders at 50×100 so it should pick 50×100, while cover renders at 100×200 so it should pick 100×200. PR #13053 adds the h descriptor and makes sizes="auto" 2D and object-fit aware.

4. Fix scale-down Upscaling (#11428)

<img srcset="logo.png 50w" sizes="auto" loading="lazy" style="width: 100px; height: 100px; object-fit: scale-down">

Authors use object-fit: scale-down or none specifically so a small 50px image won't upscale to a 100×100 container. But because w descriptors derive naturalWidth from sizes (50 / 0.5 = 100px), scale-down upscales it to 100×100 anyway! We should not inflate naturalWidth past native 1x/DPR bounds for scale-down and none.

5. Expose True File Pixels (#12565)

img.naturalWidth; // 100 (just echoes layout width!) img.resourceWidth; // 200 (true file pixels)

With w descriptors (and PR #13046), naturalWidth always equals sourceSize—so under sizes="auto", naturalWidth just echoes clientWidth. Exposing resourceWidth and resourceHeight lets RUM telemetry measure over/under-fetching and lets lightboxes check real pixel headroom.

Summary & Discussion

  • #13077: Normative selection + higher-res cache reuse
  • #13069: Density knob (densityscale)
  • #12248: 2D sizes + h descriptor for cover / contain
  • #11428: Don't upscale scale-down / none
  • #12565: True pixel dimensions (resourceWidth)

Participate: github.com/whatwg/html (issues linked above)

Together, these five issues standardize the browser baseline and give websites the knobs they need to eliminate both blurry images and wasted bandwidth.
