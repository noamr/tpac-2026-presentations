Blurry Images vs. Wasted Bandwidth

Wasted Bandwidth

  • 3x bitmaps on decorative / below-fold images (9× pixels)
  • 2×–10× width over-fetch (4×–100× pixels) on object-fit: contain

Blurry Images

  • +33–78% width needed (−44% pixels) on object-fit: cover
  • Soft zoomable heroes

Every responsive image trades off sharpness against bandwidth. Today users regularly get the worst of both worlds: wasted megabytes on decorative backdrops and letterboxed banners, and blurry images on square object-fit: cover cards and zoomable hero photos.

Who Should Hold the Knobs?

  • Browsers: Built for interop (we tried magic heuristics in Chrome & deleted them in 2024)
  • Websites: Know product hero vs. decorative blur
  • Missing knobs → lying in srcset (img?w=720 800w)

In 2014 the spec left source selection "implementation-defined" so UAs could guess bandwidth heuristics. Over a decade we learned UAs are built for interop—they can't know if an image is a conversion-critical product photo or a decorative backdrop. And when a direct knob is missing, developers bend existing attributes backwards (like lying in w descriptors), creating subtle footguns.

1. Standardize Selection (#13077)

  1. targetDensity = devicePixelRatio (UA MAY adjust for user prefs / privacy)
  2. Sort candidates by density ascending (first in document order wins ties)
  3. Select first candidate >= targetDensity, or last (largest) if none
  4. UA MAY reuse an already-loaded candidate with density > selected

Since late 2024, WebKit, Gecko, and Blink all use the same selection algorithm: sort ascending, pick the first candidate >= targetDensity, or the largest if none. We can spec this normatively, with explicit MAY allowances for user preference/privacy DPR adjustments and Chrome's cache reuse of already-loaded higher-res candidates.

2. Target Density Knob (#13069)

<img srcset="150.jpg 150w, 200.jpg 200w, 300.jpg 300w" sizes="auto" densityscale="0.75" loading="lazy" alt="">

Replaces lying in w descriptors (img?w=720 800w).

Because lying in sizes breaks sizes="auto", production sites like Airbnb literally lie in their w descriptors (writing 800w for a 720px file), which breaks CDN cache sharing and 2D aspect ratios. A densityscale knob gives sites direct control.

Why Numeric densityscale vs. Keywords?

  • srcset rungs are discrete: Sites generate specific steps (e.g. 1.3× or 1.5×) and need a predictable multiplier to step down/up one rung
  • Why UA heuristics failed: Blink removed its 3 opaque bandwidth heuristics in late 2024 because magic multipliers caused unpredictable selection
  • Exact zoom targets: A 2× zoomable hero needs densityscale="2", not an abstract resolutionpriority="high"

Why a numeric multiplier (densityscale="0.75") rather than semantic keywords like resolutionpriority="low | high"? Because srcset candidates are discrete rungs chosen by the site's image CDN, a vague "low" keyword with a UA-invented multiplier either misses the rung entirely or drops two rungs unexpectedly. And for zoomable images, the author knows the exact zoom factor (e.g. 2x).

Why an HTML Attribute Instead of CSS / sizes?

  • Why not scale sizes? Under PR #13046, sizes sets naturalWidth — scaling sizes changes intrinsic layout size!
  • Why not CSS-only? A CSS property works for loading="lazy", but eager images are fetched by the preload scanner before CSS loads — so HTML needs densityscale too

Two common questions: (1) Why not just write sizes="75px" on a 100px image? Because with w descriptors (and PR #13046), sizes determines the image's naturalWidth and intrinsic layout size. (2) Why an HTML attribute instead of a CSS property? While CSS could work for lazy images, eager images are fetched by the preload scanner before stylesheets are available, so we need densityscale in HTML regardless.

3. object-fit Selection (#12248)

<!-- Lazy: sizes="auto" reads object-fit from CSS & width/height from HTML --> <img loading="lazy" sizes="auto" width="50" height="100" srcset="s.jpg 50w, l.jpg 100w" style="object-fit: contain" alt=""> <!-- Eager: 2D sizes + h descriptor + 1D fallback --> <img sizes="cover 100px 100px, 100px" srcset="s.jpg 50w 100h, l.jpg 100w 200h" alt="">

In a 100×100 container with 50×100 and 100×200 sources, the right source depends on object-fit: contain renders at 50×100 so it should pick 50×100, while cover renders at 100×200 so it should pick 100×200. PR #13053 makes sizes="auto" 2D and object-fit aware (using the img width/height attributes for aspect ratio so lazy images don't even need h descriptors!), and adds 2D sizes="cover 100px 100px, 100px" + h descriptors for eager images.

4. Expose True File Pixels (#12565)

// <img srcset="pic-200.jpg 200w" sizes="auto" width="100" height="100"> img.naturalWidth; // 100 (equals sizes — echoes layout width!) img.imageWidth; // 200 (true bitmap pixels)

With w descriptors (standardized in PR #13046 for #3981/#3835), naturalWidth always equals sourceSize (imageWidth / density)—so under sizes="auto", naturalWidth just echoes clientWidth. Workarounds like (await createImageBitmap(img)).width allocate a duplicate decoded bitmap and throw SecurityError on cross-origin no-cors CDN images. Exposing imageWidth and imageHeight lets RUM telemetry measure over/under-fetching and lets lightboxes check real pixel headroom.

Summary & Discussion

  • #13077: Normative selection + higher-res cache reuse
  • #13069: Density knob (densityscale)
  • #12248: 2D sizes + h descriptor for cover / contain
  • #12565: True pixel dimensions (imageWidth)
  • Discussion: Where implementation-defined decisions stay for privacy

Participate: github.com/whatwg/html (issues linked above)

Together, these four issues standardize the browser baseline and give websites the knobs they need to eliminate both blurry images and wasted bandwidth.
